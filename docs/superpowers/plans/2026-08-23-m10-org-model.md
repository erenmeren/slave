# M10: The Organization Model — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A global agent-template catalog, reusable companies whose rosters are instantiated
from templates, company→project assignment that materializes independent project-local
workers, and a model-override chain that reaches the CLI — with the M0–M9 engine untouched.

**Architecture:** Four new Prisma models (`AgentTemplate`, `Company`, `CompanyTeam`,
`CompanyAgent`) plus three nullable columns on existing tables; control verbs + CLI in the
`setGoal`/`emergencyStop` idiom; one new event type through the established four-part pipeline;
model resolution at the three dispatch sites flowing to the adapter as `--model` and into the
checkpoint for exact resume replay. Headless milestone — the UI is M11.

**Tech Stack:** TypeScript monorepo — Prisma/Postgres, zod, vitest, the fake Claude CLI.

**Spec:** `docs/superpowers/specs/2026-08-23-m10-org-model-design.md`

## Global Constraints

- Full gate per task: `npm test && npm run typecheck && npm run web:build`.
- TDD per task: failing tests first, run to verify failure, implement, run green, commit.
- ONE vitest run at a time anywhere in the machine (shared test DB, TRUNCATE-per-file).
- Engine behavior is untouchable: no change to tick order, passes, guardrails, event ordering.
- `Workspace` keeps its name in code and storage (spec Decision 4); "Project" is UI copy only.
- Legacy rows (null `companyId` / null `companyAgentId`) must behave exactly as before M10.
- Commit messages end with `Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>`.

### Task 4: `assignCompany` — assignment, additive materialization, the event

**Files:**
- Modify: `packages/control/src/org.ts` (add `assignCompany`),

  `apps/orchestrator/src/cli.ts` (`assign-company` verb + USAGE)

**Interfaces:**
- Consumes: Tasks 1–3.
- Produces (the gate and M11 consume):

```ts
export interface AssignReport {
  readonly createdTeams: readonly string[]    // project Team names created this call
  readonly createdWorkers: readonly { readonly name: string; readonly role: string }[]
}
export async function assignCompany(
  workspaceId: string, companyId: string,
): Promise<Result<AssignReport, ControlRefusal>>
```

Logic (spec §5, in order): `workspace_not_found`; `company_not_found`;
`workspace.companyId` non-null AND different → `err({ kind: 'company_already_assigned',
workspaceId, companyName: <current company's name> })` (text
`` `this workspace is already run by ${companyName}` ``). Otherwise ONE transaction:
set `companyId`; for each `CompanyTeam` find-or-create a project `Team` with the same name;
for each `CompanyAgent` find a worker by `companyAgentId` — absent → create
`Agent { teamId: <matching project team>, name: companyAgent.name, role: template.role,
companyAgentId }`. Existing workers untouched (additive — spec Decision 6). After the
transaction: emit `workspace.company_assigned`
`{ company: company.name, workers: createdWorkers }` (actor `human`) — ALWAYS, even when
`createdWorkers` is empty. CLI:
`assign-company --workspace <id> --company <id>` → prints
`company assigned to <workspaceId>: <N> new worker(s)`.

- [ ] **Step 1: Failing tests.** (a) fresh workspace + a 1-team/3-agent company → 1 Team + 3
  workers exist, roles from templates, `companyAgentId` links set, one event with all three
  workers in the payload; (b) calling again immediately → `AssignReport` empty, workers still
  3, a SECOND event with empty `workers`; (c) grow the roster by one, re-run → exactly ONE new
  worker, existing rows untouched (compare ids); (d) a workspace already assigned to another
  company → `company_already_assigned`, nothing changed; (e) a workspace with a PRE-EXISTING

**Interfaces:**
- Consumes: Task 1's columns.
- Produces:

```ts
// apps/orchestrator/src/model.ts
/** worker override -> roster override -> template default -> undefined (adapter default). */
export function resolveModel(worker: {
  readonly model: string | null
  readonly companyAgent: {
    readonly model: string | null
    readonly template: { readonly defaultModel: string | null }
  } | null
}): string | undefined

// packages/control/src/org.ts
export async function setAgentModel(
  agentId: string, model: string | null,
): Promise<Result<void, ControlRefusal>>   // agent_not_found refusal; null clears
```

`resolveModel` is a pure one-liner:
`worker.model ?? worker.companyAgent?.model ?? worker.companyAgent?.template.defaultModel ?? undefined`.
Each dispatch site loads its agent with
`include: { companyAgent: { include: { template: true } } }` and passes
`model: resolveModel(agent)` in `adapter.start` input AND in `PumpRunInput.spawn`. The adapter
appends `'--model', input.model` to the CLI args when `input.model !== undefined` — on start
AND on resume (resume reads it from the checkpoint). The pump's checkpoint write records
`model: spawn.model ?? null`. `executeResume` passes `model: checkpoint.model ?? undefined`.
CLI: `set-model --agent <workerId> --model <m>` and `set-model --agent <workerId> --clear`.

- [ ] **Step 1: Failing tests.** Unit (`model.test.ts` can hold the pure cases): resolution
  precedence — worker wins over roster wins over template; all-null → undefined; legacy agent
  (null companyAgent) uses only its own column. Adapter: args contain `--model X` when set,
  absent when not; the resume path carries it (drive via the existing adapter test harness).
  Fake CLI: spawning with `--model whatever --fixture complete` still replays complete (the
  unknown flag is tolerated). Integration: a worker whose template says model `test-model-a`
