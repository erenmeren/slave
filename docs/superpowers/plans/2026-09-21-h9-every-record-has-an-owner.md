# H9 — every unfinished record has an owner (restart-chaos gate + reconciliation invariant)

Context: 2026-09-21, eight hotfixes (H1–H8) each closed one dead spot found on live projects; three of them were "the daemon restarted in the middle of a run transition and nobody picked the record up", two were "a guardrail counted the wrong thing and halted", two were "a heuristic killed a thinking worker". The person's rule: "her şey otomatik olmalı" — projects must continue on their own. H9 makes that a tested invariant instead of a list of patches.

## H9a — the restart-chaos gate (build FIRST; it drives H9b by evidence)
`scripts/gate-h9-restart-chaos.mjs`, run like the other daemon-driven gates (fake CLI env, `GATE_DATABASE_URL`, own state dir), added to `.github/workflows/ci.yml` beside m51.
- Board: one workspace, a runbook-free goal, 5 tasks in a diamond (A → B, C → D → E) planned by the fake CLI's planning arm (extend the fake or reuse an existing planning fixture), with `autoMerge: true`, `supervisorAutonomy: act`, `maxConcurrentRuns: 2`.
- Slow fixture: a `--fixture slow-work` arm in `packages/providers/test/fake-claude.mjs` that emits a tool call every `SLOW_STEP_MS` (env, default 1500) for `SLOW_STEPS` steps, with one silent gap of `SLOW_QUIET_MS` (default 4000) in the middle, then a terminal result — long enough that a restart lands mid-run, short enough for CI (≈ 20 s per run).
- Chaos loop, deterministic by `--seed`: start daemon-1; every `KILL_EVERY_MS` (default 7000) kill the daemon (alternating SIGTERM and SIGKILL — a deploy and a crash), wait for exit, start the next daemon with the same env; repeat until the board is all `done` or `CHAOS_TIMEOUT_MS` (default 240 000) passes.
- Assertions (each with the row dump on failure): every task ends `done` and integrated; no `SlaveRun` is ever non-terminal with a dead pid for longer than `RECONCILE_GRACE_MS` (60 s) across the run (sample every 2 s, keep the worst); no `guardrail.tripped` of kind `concurrency` was ever written (H9c) and at most one `circuit_breaker`; every `paused` run either resumed or concluded within 60 s; the final decision list has no `pending` row (nothing waited for a person); total `run.failed` count ≤ 2 (a kill mid-run may fail one attempt; the retry must land). Print a one-line ledger per kill: which runs were mid-transition and what the next daemon did with them.
- Also a `--kills 0` mode (no chaos) as the control: the same board must finish faster than with chaos.
- Gate scripts refuse while a host daemon runs (`scripts/lib/daemon-process.mjs` `findRealDaemonPids`): add `SLAVEOFAI_GATE_IGNORE_DAEMON_PIDS="<pid,pid>"` honoured by `findRealDaemonPids` (documented: only for a daemon known to run on ANOTHER database and state dir), so this gate can be iterated on a developer's machine.

## Findings from the 10:30 UTC restart (feed into H9b)
- F1 `stopping` runs are reconciled ONLY by `reconcileOrphans` at daemon startup (sweep.ts:238, daemon.ts:155); the per-tick sweep's SWEEPABLE excludes `stopping`. A run whose cancel FAILED ("no run found" — the adapter registry belonged to another daemon) and whose pid then died stayed `stopping` with its task `running` until an operator ran `cancel --run`. Rule: a `stopping` run with a dead pid is concluded `stopped`/`failed` by every sweep, and a `stopping` run whose pid is alive for longer than a grace is killed by pid (the sweep already has `isAlive`).
- F2 A forced daemon stop (second SIGTERM) leaves the worker children orphaned and alive with nobody reading their output; the runs stay `working` with live pids, so `deadPids` does not fire until the child exits on its own (up to `runTimeoutMs`). Rule: on a forced stop the daemon kills its own children (process group) before exiting; and a run whose pid is alive but was started by a daemon instance that is not this one (`SlaveRun.daemonId`? or a pid-file/instance token) is concluded by the new daemon after a grace — pick the cheaper mechanism.
- F3 A second daemon on the same DB is possible by operator error; the tick's claims are atomic but sweeps act on runs owned by the other instance (timeouts, cancels that fail). Rule: the daemon takes a DB-level advisory lock (`pg_try_advisory_lock`) per database on startup and refuses to start if another instance holds it; the gates' `findRealDaemonPids` pgrep check becomes redundant for correctness (keep as a courtesy).
- F4 (from `gate:h9-restart-chaos --kills 6 --seed 7 --signals kill`): three crashes in a row landed on the same task; each orphan reconciliation wrote `run.failed "the run's process (pid) is gone but the run never concluded"`, the circuit breaker counted three consecutive failures, halted the project, and the Supervisor (rules-only) escalated to a human — the board never finished. Rule: a run concluded by orphan reconciliation (or by a daemon crash in any form) is a PLATFORM failure, not a worker failure: generalise H4b's `spawnFailed` into `SlaveRun.failureClass: 'worker' | 'platform'` (migration; `spawnFailed` becomes `failureClass = 'platform'`), the breaker's consecutive count, the task's attempt count (give the attempt back) and the planning cap all ignore `platform` failures, E's `readFailure` reads it as `infrastructure`; the daemon's own crash must never cost a project a human decision. The gate's `one-circuit-breaker` and `no-pending-decision` assertions are the proof; until H9b lands, CI runs the gate with the alternate-signals default (which passes) and `--known-gaps H9-F1`.
- F5 (12:10 UTC, after the person switched both projects to Cursor): three consecutive `api_error` failures from the Claude provider (the account's rate limit) tripped the circuit breaker on a project; approving the resulting "escalate to human" cards does not lift a halt, so the project sat until an operator ran `clear-halt`. Rule (H9b R1): a provider `api_error` (rate limit, overload, auth) is a PLATFORM failure like a crash — `failureClass: 'platform'`, no breaker count, the attempt given back, and the run retried after a backoff (`PROVIDER_ERROR_BACKOFF_MS`, 60 s doubling to 10 min) instead of at once. Also: approving an `escalate_to_human` decision on a `workspace_halted` situation must clear a breaker halt when every counted failure is `platform` (or the card must say what to do) — decide in H9c.
- F6 (12:02 UTC): a Cursor worker called its `askQuestion` tool, the Cursor gate denied it ("askQuestion was denied by the permission mode"), the run failed and was retried. Cursor's question path is not wired to this system's ask/answer flow (`ask.ts`, `deliverAnswers`). Booked for the provider contract (M56a follow-up): map Cursor `askQuestion` onto `run.question_asked` → pause `waiting_for_answer` → Supervisor/person answers → resume with the answer, the way Claude's `AskUserQuestion` is handled.
