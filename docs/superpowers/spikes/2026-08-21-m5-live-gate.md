**Date:** 2026-08-21
**Claude Code version:** 2.1.239 · **Branch:** main @ 7e87306 (M5 merged)

Spec §12's gate, run against the **real** `claude`. `npm run demo` seeded workspace `6c87a795`

## What ran, and what held

- **Runs 1–3** (three notes, five-part story ×2): completed clean — too fast to pause, which is
  itself a datum: a pause window on a real run is seconds wide unless the task is long.
- **Run 4 (seven-part epic) — the intervention run:**
  - `POST /pause` mid-work → 200 `{ok:true}` → `pause_requested` → `paused`, `pauseReason:
    human`, `pausedAtStep: 3`, checkpoint written. **The pause claim chain works live.**
  - `POST /message` while paused → 200; `queuedMessage` held the instruction verbatim. **The
    slot works live.**
  - `POST /resume` → 200; the daemon claimed the intent within one tick: `resuming`, intent and
    slot cleared atomically. **The record-claim-execute lifecycle works live.**
  - The spawn was then refused (finding 1 below) — and `concludeFailedResume` (the Task 4 review
    fix) did exactly what it was built for, live: the run went `failed` with the adapter's real
    refusal as the reason instead of stranding in `resuming`. The panel showed the error; the
    task went `rework`; attempt 2 started unattended.
- **Run 5 (attempt 2) — the stop run:** `POST /stop` on a working run → 200; the process was
  SIGTERM-killed, the task went `blocked`, and the worktree survived with all seven files and
  its full git history. **Stop kills, blocks and preserves, live.**
- **Board:** `backlog → ready → running → done` movement, the `rework` task visible in the ready
  column with its true status (the Task 8 bucketing fix, live), `blocked` after the stop.

## Findings (gate-fix tasks, M3/M4 tradition)

### 1. The real CLI does not exit on a pause-gate deny — and the refused resume un-gates it

The fake adapter exits when the gate denies; **the real CLI treats the deny as a tool error and
keeps working**. Event trace from run 4: `run.paused (atStep 5)` → another `Bash` tool call →
`run.paused (atStep 6)` → a successful `Read` → the model's own words: *"Read works, so the
blockage may be transient or specific to write/exec. Retrying the write."* The child was alive
minutes after the pause was recorded.

Consequences, all observed live:

- The daemon's resume claim reached `adapter.resume`, which correctly refused: *"its previous
  process (pid 479426) is still running"*. The run failed; the operator's resume burned an
  attempt through no fault of theirs.
- `adapter.resume` clears the pause flag **before** the live-pid refusal — so the refused resume
  opened the gate for the still-live child, which resumed writing files under a run already
  marked `failed` (epics 2–7 landed this way).
- The task went `rework` and attempt 2 **adopted the same worktree while the zombie was still
  writing to it** — the git log shows duplicate "part 6"/"part 7" commits from the two writers.

The pause/checkpoint/resume machinery is all correct in isolation; what is missing is the child's
lifecycle: **recording the pause must be followed by terminating the child** (after the
checkpoint is written), the way cancel already kills with escalation. Then the pid is dead by the
time any resume arrives, and the flag-clear ordering stops mattering. Suggested shape: the pump's
pause path, after the checkpoint lands, applies `killWithEscalation` to the recorded pid; the
adapter's flag-clear moves after its live-pid check as defence in depth.

### 2. A web stop races the daemon's pump; the run concludes `failed`, not `stopped`

`requestStop` kills the process, then concludes the run. But the kill wakes the daemon's pump
first: `run.failed ("the run's output stream ended without a terminal result")` landed at seq 259,
`run.stopped ("cancelled by web operator")` at seq 260, and the row's status is whichever
conditioned `updateMany` won — here, `failed`. The task still blocks either way, but the operator
pressed stop and the UI reports a failure. In the CLI the same code never races because the CLI
process owns the pump it is killing. Suggested shape: `requestStop` marks intent (e.g. `stopping`,
which the status model already has) before the kill so the pump's conclusion path can recognise an
operator stop, or the pump's stream-ended conclusion defers to a recorded stop intent.

## Fixed on `feature/m5-gate-fixes`

Finding 1 fixed in `ddd0fe9`: the pump kills the child with escalation after the checkpoint lands
(once per pause, not per deny), and `adapter.resume` clears the pause flag only after its live-pid
refusal. Finding 2 fixed in `f863915`: `requestStop` records an explicit stop intent
(`stopRequestedBy`/`stopRequestedAt`, atomic with the `stopping` claim) before the kill; the pump
concludes `stopped` — naming the requester — only when the intent is present, so a guardrail
cancel still concludes `failed` and keeps feeding the circuit breaker. The review of the first cut
caught two would-be regressions (`resuming → working` severed; guardrail kills laundered into
`stopped`) before they merged — both now pinned by tests.

## The moral

Same as M3's and M4's: the shapes only the real CLI produces — a child that argues with a denied
tool instead of dying — are exactly the ones the gate exists to see. Every M5 surface built this
milestone behaved to spec; both findings are child-lifecycle seams between M3's process model and
the real CLI's behaviour.
