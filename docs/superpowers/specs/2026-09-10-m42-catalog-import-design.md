# M42 — External catalog import: staff a company from personas that already exist

Eighth and last milestone of the Supervisor sequence (M35 pipeline honesty, M36 messaging, M37 run context, M38 Supervisor, M39 mailbox, M40 requirement versioning, M41 scenario gate). Designed 2026-09-10 (morning, still under the overnight authorisation of 2026-09-09); every **Ruling** below took the recommended option and can be reworked by the user. "Slave" is this project's word for an AI worker.

**Goal.** An operator points the product at an external catalog of worker personas on disk — the reference format is `agency-agents` (296 Markdown files, 5-key YAML front matter `name/description/color/emoji/vibe`, a long persona body, grouped in division directories) — and imports it into the `SlaveTemplate` catalog: idempotently, re-runnable, never overwriting an operator's own edits, with an honest per-row report of what was created, updated, skipped and why. Imported templates are ordinary templates: they carry a profile (M37) that reaches a run's prompt, they can be added to a company roster and materialised into a workspace (M33/M37), and the M41 story can be staffed from them.

**Why now.** M37 gave templates a profile and M41 proved the whole pipeline with hand-written personas. The product still ships five seed templates and a form; the personas the world already wrote are the cheapest way to make a real team, and importing them exercises the profile chain, the catalog's append-only discipline and the vocabulary boundary in one go.

## 1. Rules that bind every part
- **The catalog is the product's, the persona is the source's.** A persona file is read, parsed and mapped in a PURE domain function (`packages/domain/src/catalog/persona.ts`); nothing in `packages/domain` touches disk or Prisma. The control verb does the rows; the CLI does the directory walk; the web shows the result.
- **Ruling R1 — provenance on the template.** `SlaveTemplate` gains `sourceId String? @unique` (`<catalog>/<division>/<slug>`, e.g. `agency-agents/engineering/engineering-backend-architect`), `sourceSha256 String?` (hash of the persona file as imported), `sourceDivision String?`, `importedAt DateTime?`. Templates with a `sourceId` are "imported"; everything else is hand-made. One migration, additive, no backfill.
- **Ruling R2 — per-row policy, never a bulk crash.** For each persona: (a) `sourceId` unknown and `name` free → **created**; (b) `sourceId` unknown but `name` taken by a hand-made template → **skipped `name_taken`**; (c) `sourceId` known and file sha unchanged → **unchanged**; (d) `sourceId` known, file sha changed, and the stored `profile`'s sha still equals what the last import wrote → **updated** (profile, description, sourceSha256, importedAt); (e) `sourceId` known, file changed, but the template's profile was edited by an operator since (its sha ≠ the import's record) → **skipped `locally_edited`** — the operator's words win; (f) persona body over `PROFILE_MAX_CHARS` (16 000) → **skipped `profile_too_long`** with the length (2 of 296 in the reference; the operator can shorten and re-run) — no truncation, no summarising; (g) unparsable front matter / missing `name` → **skipped `invalid_persona`** with the parser's reason. Nothing is ever deleted by an import (the `syncSkillCatalog` idiom).
- **Ruling R3 — role is the division, unless the operator says otherwise.** `SlaveTemplate.role` is a label (only `manager` and `reviewer` are load-bearing at dispatch); the importer sets `role = division` (`engineering`, `design`, …) and accepts `--role-map engineering=backend,testing=reviewer,…` to translate. No inference from names. `defaultModel`/`provider` stay null (a model choice is an operator decision — the seed's own rule).
- **Ruling R4 — the persona's words are kept, but they are labelled.** The imported profile is the persona BODY (after the front matter) verbatim, prefixed by one line the product owns: `Imported from <sourceId> on <date>; this text is the persona's own.` The vocabulary gate scans git, not the database, so imported text may say "agent" at runtime; the product's OWN strings (the prefix, the report, the UI) never do. The gate's fixture catalog (§4) is written in the project's vocabulary so nothing checked in trips `gate:m26-vocabulary`.
- **Ruling R5 — an import is recorded.** A `CatalogImport` row (`id, catalog, directory, principal (nullable), startedAt, finishedAt, created, updated, unchanged, skipped, report Json`) is written per run — the catalog has no workspace, so `ExecutionEvent` (workspaceId NOT NULL) is the wrong home; this is the auditable record. `list-imports` / the Settings page read it. No new event types.
- **Ruling R6 — the M41 residuals ride along** as the first task: (a) a sweep arm that releases a task whose `activeRunId` names a TERMINAL run (both kinds; `review` → stays `reviewing`, `implementation` → `rework` with no attempt charged), respecting `livePumpRunIds` so an in-flight conclusion in this process is never raced, with a `guardrail`-free log line and a test per kind; (b) `unblockTask` returns a task whose blocking run was a `review` run to `reviewing` rather than `rework` (`unblock.ts`), tested; (c) `cancelTask`'s refusal for `reviewing` + claim pinned (`task_run_active`); (d) `slave.message_sent`'s payload schema declares `answeredBy` (optional). Not riding along: `goalSha256` rename, auto-merge `task.integrated`, sweep RunKind union.
- **No real model call; one vitest at a time; `web:build` last; vocabulary `slave`; migrations only R1/R5; every new verb refuses with `ok()/err()` and throws inside a transaction after a write (ADR).**

## 2. Surfaces
- **Domain** `packages/domain/src/catalog/persona.ts`: `parsePersona(source: { path, text }): Result<PersonaDraft, PersonaError>` (front matter: `name` required, `description` optional, `color/emoji/vibe` read and kept in `meta`; body = text after the closing `---`); `personaToTemplate(draft, { catalog, division, roleMap }): TemplateDraft { sourceId, name, role, description, profile, sourceSha256, sourceDivision }` (description = front-matter `description`, falling back to `vibe`); `catalogSha256` = the existing `goalSha256` (general UTF-8 SHA-256; not renamed). Pure, unit-tested against three fixture texts incl. a malformed one and an over-long one.
- **Control** `packages/control/src/catalog.ts`: `importCatalog(input: { catalog: string; directory: string; entries: readonly { sourceId, division, path, text }[]; roleMap?: Record<string,string> }, principal?): Promise<Result<ImportReport, ControlRefusal>>` — one transaction per ROW (a 296-row import must not hold one lock for minutes; each row is check-then-write under `SELECT … FOR UPDATE` on the existing template when updating), then one `CatalogImport` row; `ImportReport = { importId, created: RowOutcome[], updated, unchanged, skipped: { sourceId, name, reason, detail? }[] }`; `listCatalogImports(limit)`. Refusals: `catalog_empty` (no entries), `invalid_role_map`. The directory walk lives in the CLI (`readCatalogDirectory(dir, { divisions? })` in `apps/orchestrator/src/catalog.ts`: reads `divisions.json` when present to know which top-level dirs are divisions, else every dir; skips `README.md`/`CONTRIBUTING.md`; recurses one level for tool subfolders; `sourceId = <catalog>/<division>/<relative-path-without-.md>`).
- **CLI** `import-catalog --dir <path> [--catalog <name>] [--division <d>[,<d>]] [--role-map a=b,…] [--dry-run] [--by <principal>]` prints the report (counts, then one line per created/updated/skipped row with the reason); `--dry-run` runs the parser and the policy without writing (the policy reads the DB) and prints what WOULD happen; `list-imports [--limit n]`.
- **Web** (Settings → template catalog): imported templates show a `source` chip (division + catalog) and "imported <date>"; a read-only "Catalog imports" list (last 10 runs with counts) under the templates table; no upload/import form (the catalog is a path on the daemon host's disk, like skills). Routes: `GET /api/org/catalog-imports`. `listTemplates()` gains `sourceId/sourceDivision/importedAt`.
- **Gate `gate:m42-catalog-import`** (fake CLI, real daemon): a checked-in fixture catalog `scripts/fixtures/catalog-m42/` (in the project's vocabulary): `divisions.json` with two divisions, five personas — a normal one, one whose name collides with a hand-made template, one over `PROFILE_MAX_CHARS`, one malformed, one that the gate rewrites between runs. Stages: (1) first import creates 2, skips 3 with the three reasons; `CatalogImport` row exact; (2) second import: 2 unchanged; (3) the gate edits one imported template's profile through `set-profile` and rewrites its file → `locally_edited`; rewrites the other file → `updated`; (4) `--role-map` on a `--dry-run` writes nothing and prints the translation; (5) a company built from the two imported templates is assigned to a workspace (real CLI), a task is dispatched under a daemon with `m8a-flow`, and the run's recorded `RunContext` carries the imported persona (its prefix line and a sentence from the body) — the persona is in front of the model; (6) teardown. README `## Importing a catalog` + roster 17 → 18; CI.

## 3. Out of scope
Importing skills/tools from personas (`tools:` lines are kept in `meta`, not acted on); colours/emoji in the UI (kept in `meta`, unused); summarising over-long personas; a web upload; importing straight into a company (assignment stays the operator's act); vendoring `agency-agents` into the repo (licence is MIT, but the vocabulary gate and repo size say no — the gate uses its own fixture catalog).

## 4. Errata — where execution corrects this spec
(appended during execution)

Found while writing the plan (2026-09-10 morning, before Task 1); each is baked into `docs/superpowers/plans/2026-09-10-m42-catalog-import.md`. Full reasoning with code citations is in the plan's companion notes (session scratchpad); summarised here.

- **E1 (amends §2 Web).** The template catalog lives on the projects home page (`ProjectsClient`'s `team-catalog` section), not Settings; the `source` chip and the read-only "Catalog imports" panel go there, and `apps/web/src/app/page.tsx` reads `listCatalogImports()` beside `listTemplates()`. **E21:** the chip renders inside the existing Name cell — the six-track grid `gate:m14-fidelity` screenshots gains no column.
- **E2 (amends R1/R2e).** `locally_edited` is undecidable from `sourceSha256` (the FILE's hash) because `setProfile({ templateId })` records nothing and the old body is gone from disk. `SlaveTemplate` gains `profileSha256 String?` = `goalSha256` of the exact profile text the import stored; `locallyEdited = (profile === null ? null : goalSha256(profile)) !== profileSha256` (also catches a cleared profile). **D11:** `unchanged` compares the file sha only.
- **E3 (amends R2f).** The 16 000 cap is measured on the COMPOSED profile (prefix line + body), because `buildRunContext` refuses a run whose stored profile exceeds it; the check lives in the pure `personaToTemplate`, which returns a `Result` (E20: its bag is `{ catalog, division, slug, text, importedAt, roleMap? }`).
- **E4 (amends R5).** `CatalogImport.principal` → `by String?` (an operator name from `--by`; the CLI has no `Principal`).
- **E5 (amends R4).** The reference catalog's directory name contains the forbidden word, so no product string, comment, README line, test or default may name it; `--catalog` defaults to `basename(dir)` at runtime and every checked-in example uses the fixture catalog `catalog-m42`.
- **E6 (amends R6a).** The stranded-claim release is a NEW sweep arm `reconcileStrandedClaims(deps)` (reported as `SweepReport.strandedClaims`), not the M41 releases: a task whose `activeRunId` names a TERMINAL run (`stopped|succeeded|failed`); guarded by `livePumpRunIds`, a `STRANDED_CLAIM_GRACE_MS = 30_000` floor on `terminalAt` (another process's in-flight conclusion), and a status-guarded write (`review` → claim only; `implementation` → `rework` only while `running`, no attempt; `task.rework` for the implementation kind only).
- **E7 (amends R6b).** `unblockTask` decides by the task's most recent run's kind, and returns to `reviewing` ONLY while `reviewAttempts < REVIEW_RETRY_CAP` (otherwise `dispatchReview` re-parks it next tick — an unblock that undoes itself); at the cap it goes to `rework` as today. `REVIEW_RETRY_CAP` moves to `packages/domain/src/review/cap.ts`; `unblockTask` returns `Result<{ status: 'rework' | 'reviewing' }>` and `task.unblocked` gains an optional `status`. No attempt ceiling check on the `reviewing` path.
- **E8/E9.** R6(c) is a pinning test only (`cancelTask` already checks the claim first); R6(d) is `answeredBy: z.string().min(1).optional()` on the `slave.message_sent` payload.
- **E10 (amends R3).** `role` is append-only and copied into `runtimeRoles` at materialisation, so `--role-map` applies at CREATION only; an `updated` row never writes `name`/`role`, and a differing mapped role is reported as `roleDrift { stored, mapped }` with the CLI saying how to change it (delete and re-import).
- **E11–E19.** Boolean CLI flags go LAST (`parseArgs` takes the next token as a value); roster verbs are `add-team`/`add-slave`; the parser imports neither `node:fs` nor `node:crypto` (the domain reaches the web client bundle) and hashes via `goalSha256`; the seed's TRUNCATE list gains `CatalogImport`; test placement per the `unit`/`integration` vitest projects; a new refusal kind has three homes (`ControlRefusal`, `refusalText`, `ALL_KINDS`) and `catalog_empty`/`invalid_role_map` map to 409; the gate asserts the manifest's profile source `{ origin: 'template', sha256 }` plus the prefix line and a body sentence in `RunContext.prompt`; `divisions.json` is `{ divisions: { <dir>: {…} } }` with a fallback to every subdirectory; `importCatalog` writes `slaveTemplate.create` itself (provenance columns) and reuses `isUniqueConstraintViolation`.
- **Decisions D1–D11:** `profileSha256`; no role rewrite; `basename(dir)`; reconciler in `sweep.ts`; no events (the `CatalogImport` row is the record); a `--dry-run` writes no row; one transaction per row + one `create` for the import row (a refusal after a write throws); 30 s grace; `unblockTask`'s widened return; the fixture catalog is vocabulary-clean and NOT excluded from the gate; `unchanged` compares the file sha only.
- **E22 (amends E6/D8, found in Task 1 review).** A flat 30 s grace does not cover ANOTHER process's verify window: after a `succeeded` write the chained `verifyConcludedRun` may run the workspace's verify commands for up to `runTimeoutMs` each before `advance()` releases the claim, and a CLI `tick`/`resume-run` legitimately runs that chain beside a live daemon. The grace is therefore per kind: `review` (DB-only conclusion) keeps `STRANDED_CLAIM_GRACE_MS`; `implementation` uses `STRANDED_CLAIM_GRACE_MS + runTimeoutMs × max(1, verifyCommands.length)` read off the workspace row the sweep already loads. An implementation strand thus self-heals after the longest verify the workspace allows, never before. Backlog: `advance()`'s `reviewing` write is guarded on status, not on the run id.
- **E23 (found in Task 2).** The plan's `prisma migrate diff` flags (`--from-schema-datasource`, `--to-schema-datamodel`, `--shadow-database-url`) are Prisma 6; under Prisma 7.9 the proof is `npx prisma migrate diff --from-config-datasource --to-schema packages/db/prisma/schema.prisma --config packages/db/prisma.config.ts` → "No difference detected", optionally repeated against a throwaway database replayed from the migrations directory (never `--from-migrations` against the dev or test DB, which resets it).
