# M48 — Typed handoffs + runbooks

Fifth milestone of the roadmap `2026-09-10-roadmap-m44-m56.md`, on M47's capability graph. Designed 2026-09-11 from an inventory of the planning graph, the run-context sections, messaging, the Supervisor, verify/review, the persona mapper and the project surfaces (session scratchpad `m48-explore.md`). Every **Ruling** took the recommended option under the user's standing approval. "Slave" is this project's word for an AI worker.

**Goal.** Work is handed over with a contract, not a paragraph: every planned task carries a typed handoff (objective, expected output, acceptance criteria, known constraints, evidence required, context references) that the worker, the reviewer and the Supervisor all read from the same row. A **runbook** is a reusable stage plan (design → implement → verify → review → release, or a persona's own workflow) with per-stage capabilities, gates, retry and escalation; the Supervisor recommends one for a goal, a human adopts it, the manager's planning run adapts it into the task graph, the domain measures how well the graph follows it, verify runs the stage's gates, and the Overview shows the current stage. A runbook SUGGESTS a roster (its capabilities feed M47's team formation); it never creates a team.

**Facts the design stands on** (from the inventory). Nothing named runbook/handoff/stage/acceptance exists outside `MessageKind.handoff` and the persona regex; the whole text a worker sees about its task is `Task: ${title}\n\n${description}` (`runContext.ts:663`) and the Supervisor answers questions from the same two columns (`answerPrompt.ts:174-177`); `verifyCommands` are per workspace only; `PLANNING_GRAPH_INSTRUCTIONS`/`REPLAN_INSTRUCTIONS` are byte-pinned and carry the fake CLI's routing literals, so per-workspace planning material goes in a run-context SECTION (M47 E3 precedent); a new event type touches six exhaustive sites; the persona mapper already lifts `Step`/`Phase` lines into `ProfileSpec.workflow`.

## 1. Rulings
- **R1 — The typed handoff is a JSON column on the task, validated in the domain.** `packages/domain/src/handoff/contract.ts`: `HandoffContract { objective: string; expectedOutput: string; acceptanceCriteria: string[]; knownConstraints: string[]; evidenceRequired: string[]; contextReferences: string[] }` with `handoffContractSchema` (`.strict()`, every string ≤ 400 chars, every list ≤ 12 items, `objective` and `expectedOutput` required, lists default `[]`), `renderHandoff(contract): string` (deterministic, heading `HANDOFF`, one labelled block per non-empty field, code-point safe, never contains the routing literals `"task graph"`, `"verdict"`, `"replan"`, `"sources"`, `"candidateIndex"`). Storage: `Task.handoff Json?` (null = hand-made or pre-M48 task; never backfilled) and `Task.stage String?` (the runbook stage key, R3). Dependencies stay `TaskDependency` (not duplicated in the contract).
- **R2 — The planner emits the contract and the stage.** `planTaskSchema` gains optional `handoff` (the contract shape, all fields optional at the shape, defaults applied) and optional `stage: string`; `validateStructure`/`validateDelta` enforce the caps and, when the workspace has a runbook, that `stage` names one of its stage keys (a structural error names the key). `concludePlanning`/`applyDelta` write `Task.handoff` (null when absent), `Task.stage`, and `Task.maxAttempts` from the stage's `retry.maxAttempts` when the stage sets one (else the workspace value as today). `workspace.plan_created` / `workspace.replanned` payloads gain optional `runbook: { id, key, stagesCovered: string[], stagesMissing: string[] }` — the measured adherence (soft: a plan that skips a stage is not refused; the gap is visible). Because the planning instructions are byte-pinned, the request for `handoff`/`stage` is a new run-context section `runbook` (R4) rendered after `capabilities`; when no runbook is adopted, a shorter `handoff_protocol` section asks for the contract alone. Fake-CLI fixtures `plan-graph-runbook.ndjson` (stages + contracts) exercise both.
- **R3 — Runbooks are data: a `RunbookTemplate` table with a checked-in seed and a persona translation.** Columns: `id`, `key` (unique slug), `name`, `description`, `keywords String[]` (whole-word goal matching, R5), `requiredCapabilities String[]`, `optionalCapabilities String[]`, `stages Json` (validated `RunbookStage[]`: `key`, `title`, `objective`, `capabilities: string[]`, `dependsOn: string[]` (stage keys, acyclic), `expectedOutputs: string[]`, `gates: string[]` (shell commands run by verify for tasks in this stage, in addition to the workspace's `verifyCommands`), `retry: { maxAttempts: number } | null`, `escalation: string | null`), `source: 'seed' | 'persona' | 'human'`, `sourceTemplateId String?` (the persona it was translated from, SET NULL), `createdAt`, `updatedAt`. Domain `packages/domain/src/runbook/{spec,adherence,recommend,fromPersona}.ts`: `runbookStagesSchema`, `stageOrder(stages)` (topological, deterministic), `measureAdherence(runbook, tasks)`, `recommendRunbooks(goal, runbooks, roster)`, `runbookFromProfileSpec(spec, template)` (each `ProfileSpec.workflow` item → one stage `step-N` with the template's `capabilityKeys`, linear `dependsOn`, no gates, `source: 'persona'`, `keywords` = the template's capability labels; only when `workflow.length ≥ 2`). Seed (`packages/db/src/runbooks.ts`): `feature-delivery` (design → implement → verify → review → release), `bug-fix` (reproduce → fix → verify → review), `security-review` (threat-model → review → remediate → verify), each with real capability keys from the M47 seed, `gates: []` (a gate is a workspace's own command, the seed cannot know it), `retry` on the verify stages, `escalation` sentences. Written by `db:seed` and by an idempotent `syncRunbooks()` (seed rows only; `human`/`persona` rows untouched). `importCatalog` runs the persona translation per created/updated template after M46's spec mapping (upsert by `(source:'persona', sourceTemplateId)`; never overwrites a `human` row).
- **R4 — The contract and the runbook reach every party through run-context sections.** New `SectionKind`s: `handoff` (implementation and review orders, right after `task`; source `{ kind: 'handoff'; taskId; sha256 }` — its own hash so M37/M41's `task.sha256` stays title+description), `runbook` (planning order, after `capabilities`; source `{ kind: 'runbook'; runbookId; key; stageKeys: string[] }`; text = the stages in `stageOrder` with objective/capabilities/dependencies/expectedOutputs and the exact JSON shape to emit), `handoff_protocol` (planning order, same slot, when no runbook; source `{ kind: 'handoff_protocol' }`). The Supervisor's answer prompt (M39) `task` source arm gains `objective`, `expected output` and `acceptance criteria` lines from the contract when present (still title+description first; sources remain quoted from the task text). `MessageKind.handoff` is not used by M48 (a message is a slave's word; the contract is the board's).
- **R5 — The Supervisor recommends, a human adopts, the workspace remembers.** `Workspace.runbookId String?` (FK `RunbookTemplate`, SET NULL). Situation `runbook_recommended` (13th; subject = workspace id; raised when the workspace has a goal, no runbook and zero tasks — before the first plan) with candidates from `recommendRunbooks(goal, runbooks, roster)`: score = whole-word keyword hits in the goal text (`normaliseCapabilityText` rules) × 10 + covered required capabilities (roster capabilities/roles via M47's projection) − missing required capabilities; ties by `key` ascending; top 3 become `adopt_runbook { runbookId, key, name, rationale }` offers (rationale names the matched words and the covered/missing capabilities in labels), tier `proposed`; no keyword hit anywhere → no situation (silence beats noise). `applyDecision` arm sets `Workspace.runbookId` and appends `workspace.runbook_adopted { runbookId, key, name }` (50th event type; lane `plan_change`; activity card). CLI `runbooks sync|list|show <key>|add --file <json>` and `adopt-runbook --workspace <id> --runbook <key>` (human adoption without a decision; same event, actor human) and `adopt-runbook … --clear`. Adopting after tasks exist is allowed (the next re-plan sees it); the planning section is only rendered for the run that plans.
- **R6 — Stage gates, retry and escalation are real.** `verifyConcludedRun` appends the task's stage `gates` (looked up through `Workspace.runbookId` + `Task.stage`) after `verifyCommands`; the verify log names which command was the stage's; `Task.maxAttempts` came from the stage at creation (R2); when `rejectTask` exhausts attempts on a task with a stage whose `escalation` is set, the `task_failed` situation's summary carries the stage's escalation sentence and `escalate_to_human.summary` repeats it. `measureAdherence` also yields the **current stage** = the first stage in `stageOrder` with any non-terminal task (or the last stage when every task is terminal); exposed on the Overview (R7) and by CLI `runbook-status --workspace <id>`.
- **R7 — Surfaces.** Overview: a `RunbookPanel` between the request box and the timeline — no runbook: the recommended runbooks (name, why, stages count) each with an Adopt button (via the pending `adopt_runbook` decision when one exists, else `POST /api/w/:id/runbook` with `{ key }`), plus a picker of every runbook; adopted: name, current stage, the stage list with status (done / active / pending / missing from the plan) and the required capabilities as label chips marked covered/uncovered (M47's `teamPlanOf`). Tasks tab: the task drawer/page shows the contract under a `DetailsGroup group="handoff"` (new `DetailsGroupName`) and the stage as a chip. Workforce: a fifth tab `runbooks` (`/workforce?tab=runbooks`) listing seed/persona/human runbooks with a read-only drawer (stages, capabilities as labels, source, the persona it came from). Routes: `GET /api/org/runbooks`, `GET /api/org/runbooks/:key`, `GET/POST/DELETE /api/w/:id/runbook`. `docs/ia.md` gains the rows. Copy prints labels, never keys.
- **R8 — Gate.** `gate:m48-runbooks` (real daemon + fake CLI + Playwright): seed and sync runbooks; import `scripts/fixtures/catalog-m48/` (one persona with a three-step Workflow Process → a persona runbook appears; one without → none); a workspace whose goal contains a `feature-delivery` keyword and a roster covering some of its capabilities → `runbook_recommended` with `adopt_runbook` first offer `feature-delivery`, pending; approve via the real CLI → `Workspace.runbookId` set, `workspace.runbook_adopted` event; the planning run answered from `plan-graph-runbook` → tasks carry `stage`, `handoff`, stage `maxAttempts`; `plan_created.runbook.stagesMissing` names the stage the fixture skips; a work run's recorded `RunContext` contains the HANDOFF section with the objective and the acceptance criteria and the `handoff` manifest entry with its sha; the review run's context too; a stage gate command (`true` on the implement stage; a deliberately failing one on a second workspace) runs in verify and its failure is attributed to the stage in the log/event; `runbook-status` prints the current stage; in a real browser: the Overview panel shows the runbook, the current stage, the stage list with one `missing` stage and the capability chips; the Workforce runbooks tab lists three seed + one persona runbook; the task drawer shows the contract. `organization`/`overview` m14 PNGs regenerate in their own commit. README roster 22 → 23; CI step after `gate:m47-team-formation`.
- **Never a real model call; one vitest at a time; `web:build` last, never beside `next dev`; vocabulary `slave`; migrations additive with the Prisma 7 diff proof; `decide()` unchanged; the M47 gates unchanged; a refusal after a write inside a transaction throws; refusal kinds in three homes; no product string names the reference persona catalog.**
