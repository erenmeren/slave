# M46 — Rich specialist profile + Workforce Catalog

Third milestone of the roadmap `2026-09-10-roadmap-m44-m56.md`, on M42's importer and M44/M45's primitives. Designed 2026-09-11 from an inventory of the profile chain, the importer, 274 persona files' heading structure, runtime roles, skills and the catalog surfaces (session scratchpad). Every **Ruling** took the recommended option under the user's standing approval. "Slave" is this project's word for an AI worker.

**Goal.** A template becomes a SPECIALIST PROFILE with structure — identity, summary, mission, a suggested runtime role, capabilities, expertise, operating principles, constraints, workflow, deliverables, success criteria, collaboration hints, recommended skills, and a source record (repository, path, revision, license, imported at) — kept distinct from the RUNTIME ROLE the scheduler dispatches on. Imported personas are mapped into that structure (a representative subset of headings; imported ≠ active); an operator's field-level customisations survive upstream updates; and the Workforce Catalog replaces template management: search, filter by capability/domain/source/expertise/skill, inspect, customise, see overrides, update safely — raw Markdown only under Advanced. Nothing changes what a run receives except that the profile Markdown is now rendered from the effective structured profile within the same 16 000-character cap.

## 1. Rulings
- **R1 — Two JSON columns on the template, one renderer.** `SlaveTemplate.profileSpec Json?` (UPSTREAM, importer-owned; `profileSpecSchema` zod over `{ identity, summary, mission, runtimeRole, capabilities[], expertise[], operatingPrinciples[], constraints[], workflow[], deliverables[], successCriteria[], collaborationHints[], recommendedSkills[], source{ repository, path, revision, license, importedAt, mappingQuality } }`, every list an array of short strings ≤ 240 chars, ≤ 40 items) and `SlaveTemplate.profileOverrides Json?` (LOCAL, operator-owned: a PARTIAL object of the same shape holding only the fields the operator changed). `effectiveProfileSpec(spec, overrides)` (pure, `packages/domain/src/profile/spec.ts`) merges field by field (an overridden list replaces the upstream list). The existing Markdown `profile` column is DERIVED: `renderProfileSpec(effective)` (pure) produces the Markdown the run-context builder already renders, truncating whole sections from the end in a fixed priority order (identity, mission, constraints, operatingPrinciples, capabilities, expertise, workflow, deliverables, successCriteria, collaborationHints, skills) so the result never exceeds `PROFILE_MAX_CHARS`; it is rewritten whenever the spec or the overrides change. `effectiveProfile`'s chain (slave → company → template Markdown) and the run-context section are unchanged. Why: the prompt path stays one Markdown block with its proven cap; the structure lives beside it; cost if wrong: a renderer.
- **R2 — Overrides survive upstream updates because they live apart.** The importer (M42's `importCatalog`) writes `profileSpec` on `updated` rows and re-renders `profile` from the NEW effective spec (upstream + untouched overrides); M42's whole-blob `locally_edited` rule now applies only to a RAW Markdown override (R5): if the operator set the Markdown by hand, the row is skipped as before. `setProfileOverrides(templateId, patch, actor)` validates the patch against the schema, stores it, re-renders `profile`; `clearProfileOverride(templateId, field)`. A `template.profile_overridden` event is NOT written (catalog rows have no workspace — M42 R5); the `CatalogImport` report row records `overridesKept: n` per updated row. Why: field-level survival without version tables; cost if wrong: a merge function.
- **R3 — The mapper is a pure heading map with an honest quality mark.** `personaToProfileSpec(draft: PersonaDraft, source)` in `packages/domain/src/catalog/spec.ts`: H1 + the first paragraph → `identity`/`summary` (summary falls back to front-matter `description`, then `vibe`); `Identity & Memory` bullets → `identity` (Role/Personality lines) and `expertise` (Experience/Expertise lines); `Core Mission` → `mission` (first sentence) + `capabilities` (H3 sub-headings, else top bullets); `Critical Rules You Must Follow` → `constraints` (lines with MUST/NEVER/ALWAYS/DO NOT) and `operatingPrinciples` (the rest); `Technical/Architecture/… Deliverables` → `deliverables` (H3 names); `Workflow Process`/`Your Process` → `workflow` (Step/Phase lines); `Success Metrics` → `successCriteria`; `Advanced Capabilities`/`Core Capabilities`/`Specialized Skills`/`Domain Expertise` → `capabilities`/`expertise`; any `Integration with …`/`Working with …`/`Collaboration …` section and sentences matching `consult|pair with|hand off|escalate to|work with the <Title>` → `collaborationHints` (verbatim sentences; M47 normalises them); `Communication Style`, `Learning & Memory` → not mapped (they stay in the Markdown body). `recommendedSkills` come only from an explicit `skills:` front-matter key (comma list) — the `tools:` key names base tools, not this catalog's skills, and is ignored. `runtimeRole` = the template's `role` (division or role-map). `source.mappingQuality` is `full` (≥ 7 canonical headings matched), `partial` (≥ 3), or `none`. The `Requested`-style prefix line stays on the rendered Markdown. Why: 75–82 % of the reference catalog shares one skeleton; the rest degrades honestly; cost if wrong: a heading table.
- **R4 — Source record.** `source.repository` = the catalog name (M42's `--catalog`/`basename(dir)`), `path` = `<division>/<slug>.md`, `revision` = `git rev-parse HEAD` of the directory when it is inside a git work tree, else null (the walk in `apps/orchestrator/src/catalog.ts` reads it once per import), `license` = the SPDX-like first line of a `LICENSE` file at the catalog root when present (`MIT License` → `MIT`), else null; `importedAt`. Two additive columns mirror the two new facts for listing (`SlaveTemplate.sourceRevision`, `sourceLicense`). No vendoring; attribution rendered in the catalog's Source group (M55 relies on it). Why: provenance the prompt asks for, cheaply; cost if wrong: two nullable columns.
- **R5 — Raw Markdown is an Advanced override, not the editor.** The structured editor writes overrides (R2). `setProfile({ templateId })` (the free-text Markdown write) remains under Advanced as "raw override"; when set, it wins over the rendered Markdown and the row shows a `raw override` marker; M42's `locally_edited` skip protects exactly that case. Slave-level and company-level Markdown overrides are unchanged (M37). Why: no data loss, one clear precedence; cost if wrong: a marker.
- **R6 — Workforce Catalog UI replaces template management.** `/workforce?tab=catalog` becomes the catalog (`WorkforceCatalog`): search (name, summary, expertise, capabilities), filters (division/domain, capability, source `imported | local`, skill), rows = name · summary · division · up to three capability chips (+N) · source chip (`imported · <repository>` / `local`) · `overridden` marker; a row opens `ProfileDrawer` (M44 `Drawer`) with `DetailsGroup`s Identity · Mission · Capabilities · Expertise · Principles · Constraints · Workflow · Deliverables · Success criteria · Collaboration · Skills · Source, a `Customise` mode editing any field into an override (`overridden` badge per field, `Reset` per field), and `Advanced ▾` holding the rendered Markdown, the raw override editor, and the M42 import history. Hand-made templates keep their form (`template-form`, `gate:m11-shell` drives it) and companies keep `CompanyManager` under the same tab. Read model `listWorkforceCatalog({ q, division, capability, source, skill })` filters in memory over the JSON column (hundreds of rows; no join tables — M47's taxonomy may add them). Why: the prompt's catalog concept on M44's primitives; cost if wrong: a tab.
- **R7 — Gate.** `gate:m46-workforce-catalog` (Playwright + real CLI, fake CLI env): the fixture catalog gains a canonical nine-heading persona, a divergent-skeleton persona and one with a collaboration table (vocabulary-clean, D10); the fixture directory is copied into a temp git repo so `revision` is asserted, with a `LICENSE` file so `license` is `MIT`; import → assert `profileSpec` fields per persona, `mappingQuality` full/partial/none, the source record, the rendered Markdown ≤ cap and byte-equal to `renderProfileSpec`; customise one field via the UI → override stored, Markdown re-rendered; change the upstream file → re-import → the override survives, other fields update, `overridesKept 1`; set a raw override → re-import skips `locally_edited`; UI: search narrows, capability/source filters work, the drawer's groups show the fields, raw Markdown only under Advanced; a materialised worker's run context still renders the profile section from the Markdown (one fake-CLI run, m8a-flow). README `## Specialist profiles` + roster 20 → 21; CI; fidelity regenerate if `/workforce` changes (it does: the catalog tab is not the default tab — confirm and regenerate only if a screenshotted page moved).
- **Never a real model call; one vitest at a time; `web:build` last, never beside `next dev`; vocabulary `slave` (fixture personas included); migrations additive with the Prisma 7 diff proof; no product string names the reference catalog (M42 E5); a refusal after a write inside a transaction throws.**

## 2. Surfaces after M46
Domain: `profileSpecSchema`, `effectiveProfileSpec`, `renderProfileSpec`, `personaToProfileSpec`, label tables for the twelve groups. Control: `importCatalog` writes `profileSpec`/`profile`/source columns and keeps overrides; `setProfileOverrides`, `clearProfileOverride`; `listWorkforceCatalog`. Orchestrator: the walk records `revision`/`license`. Web: `WorkforceCatalog`, `ProfileDrawer`, routes `GET /api/org/catalog`, `PATCH /api/org/templates/:id/overrides`, `DELETE …/overrides/:field`. CLI: `show-profile --template <id>` prints the effective spec; `import-catalog` unchanged. Migration: `profileSpec`, `profileOverrides`, `sourceRevision`, `sourceLicense`.

## 3. Out of scope
Capability taxonomy and matching (M47); normalising collaboration hints into relationships (M47); slave/company-level structured overrides (Markdown overrides stay); a web import form (the catalog is a path on the daemon host); colour/emoji; summarising over-long personas (the renderer truncates by section instead); the full catalog import (M55).

## 4. Errata — where execution corrects this spec
(appended during execution)

Found while writing the plan (2026-09-11, before Task 1); each is baked into `docs/superpowers/plans/2026-09-11-m46-workforce-catalog.md`. Reasoning with file citations is in the plan's companion notes (session scratchpad); summarised here.

- **E1/E2 (amend R1).** `ProfileSpec` gains `body` (the persona's own prose — unmapped sections live there, so a `none`-quality persona is not a two-line worker); the renderer's truncation priority is thirteen entries: identity, summary, mission, constraints, operatingPrinciples, capabilities, expertise, workflow, deliverables, successCriteria, collaborationHints, recommendedSkills, body (last; truncated first). M42's tests and gate stay green untouched.
- **E3 (amends R1).** `runtimeRole` is never rendered into the prompt (the scheduler matches `Slave.runtimeRoles`; the line could be false).
- **E4/E5 (amend R2/R5).** No marker column: a raw Markdown override is `profileSpec parsed && profile !== null && goalSha256(profile) !== profileSha256` — the expression `importCatalog` already evaluates for `locally_edited`, scoped to rows with a spec (hand-made templates have `profileSha256 = null`); `setProfileOverrides` re-stamps `profileSha256` after re-rendering, or every customisation would freeze its row against imports.
- **E6 (settles R2 vs M42 R2f).** `profile_too_long` stays where M42 put it (the composed raw profile before mapping; `gate:m42` asserts the skip); the renderer's truncation is a second, independent guarantee.
- **E7/E8/E9/E10/E11 (amend R6/§2).** The import history stays one panel on the tab (under its own Advanced), not a group in every drawer; `DetailsGroupName` widens with the twelve profile groups; ONE read model `listWorkforceCatalog` (facets computed before filtering; `listTemplates()` = its rows) so `/workforce` does not read templates twice; a fourth route `GET/PUT /api/org/templates/:id/profile` (the full effective spec on demand for the open drawer — ~3 KB must not ride on every row — and the raw override, which has no web verb today); catalog filters write the URL with `history.replaceState` (the page is `force-dynamic` with eight loaders incl. a disk scan).
- **E12/E13 (amend R7).** m14 screenshots `/workforce`'s DEFAULT (Slaves) tab — no fidelity regeneration; `gate:m11-shell` needs no repoint provided the catalog keeps `DataTable`/`Row` and `template-form`'s testids.
- **E14/E15 (amend R4).** The git/licence reads live in the orchestrator walk (`execFileSync git rev-parse HEAD`; `LICENSE` → `LICENSE.md` → `LICENSE.txt`, first non-empty line, `/^(.{1,60}?)\s+Licen[cs]e$/i` → group 1, else the line when ≤ 60 chars, else null), never in the domain.
- **E16 (amends R7).** The gate gets its own fixture catalog `scripts/fixtures/catalog-m46/` (four personas: canonical nine-heading, divergent, collaboration table, `none`; a `LICENSE` with `MIT License`; copied into a temp git repo) — adding to `catalog-m42` would break that gate's exact counts.
- **E17/E18/E19/E20.** Three new refusal kinds in three homes (`profile_not_structured`, `invalid_profile_overrides`, `unknown_profile_field`); `server-org.test.ts`'s whole-object `toEqual` rows widen in the same commit; `Drawer` widths are whole literals (`w-[640px]`); no product string names the reference catalog.
- **Decisions D1–D11:** two JSON columns; in-memory filtering; row summaries in the list, the full spec on demand; a hand-made template cannot be given structured overrides (`profile_not_structured`); one field, one Save; clearing the last override writes `DbNull`; `show-profile` prints JSON by default, `--markdown` for the rendered text; the catalog row keeps its Default model cell (M12); the gate is one script, browser and daemon both; `overridesKept` is printed by `describeImport`; naming `overriddenFields` on a row vs `profileOverrides` on the template.
- **E21 (Task 1 review; amends E1).** `body` is the UNMAPPED REMAINDER of the persona (the sections the heading map did not consume, e.g. Communication Style, Learning & Memory, plus any unrecognised section), not the whole persona: rendering fields + the whole persona doubled every mapped constraint and made the preserved sections the first casualty of the cap. The renderer never returns an empty string: when a single section alone exceeds the cap the composition is hard-sliced on a code-point boundary. `source.importedAt` is an ISO datetime in the schema (a hand-edited row is refused at read time, never rendered as a false sentence). `runtimeRole` is not overridable (metadata; the scheduler matches `Slave.runtimeRoles`).
- **E22 (Task 2 review; amends R2).** A template imported before M46 has no `profileSpec`, and an unchanged file must still get one: on an `unchanged` row whose `profileSpec` is null and which carries no raw override, the importer writes `profileSpec`, `sourceRevision`/`sourceLicense`, the rendered `profile` and re-stamps `profileSha256` (the row stays `unchanged` in the report, with `structured: true`); M42's locally-edited-with-unchanged-file case still writes nothing. Provenance (`sourceRevision`) is refreshed only when the file changed or the row was first structured — an unchanged file keeps the revision it came from. The division filter matches `sourceDivision` only — the facet list is the definition of "division" on this surface; hand-made templates are reached through `source: local` and free text. The raw-override predicate treats a cleared (`null`) profile exactly as the importer's `locally_edited` does.
