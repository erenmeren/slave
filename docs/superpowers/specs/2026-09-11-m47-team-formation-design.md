# M47 — Capability graph + minimal team formation

Fourth milestone of the roadmap `2026-09-10-roadmap-m44-m56.md`, on M46's structured profiles. Designed 2026-09-11 from an inventory of dispatch matching, Supervisor staffing, the M46 profile fields, the organisation surfaces and the persona collaboration text (session scratchpad). Every **Ruling** took the recommended option under the user's standing approval. "Slave" is this project's word for an AI worker.

**Goal.** The Supervisor chooses workers by CAPABILITY, not by name: a data-driven dotted taxonomy (`backend.api-design`, `security.application`, …); tasks declare the capabilities they need; the roster is measured against them; what is missing is found in the company roster or the catalog; the minimal team is proposed with a rationale a person can read ("Security Specialist added because authentication work requires `security.application`"), preferring an existing capable worker > an existing company worker > a new project worker > a temporary specialist (M50 gives temporary its lifecycle; here it is a flag on the proposal). Persona collaboration hints become advisory relationships, never execution authority. Dispatch keeps ONE matching rule.

## 1. Rulings
- **R1 — The taxonomy is data.** A `Capability` table: `key` (dotted, `<domain>.<name>`, primary), `label`, `domain` (the prefix), `role` (the runtime role this domain projects to — R2), `synonyms String[]`, `createdBy` (`seed | human`). Seeded from `packages/db/src/capabilities.ts` (a checked-in list covering the reference catalog's divisions: backend, frontend, security, database, qa, operations, product, design, data, mobile, …, ~60 keys) by `db:seed` AND by an idempotent `syncCapabilityTaxonomy()` run at import time and by the CLI `capabilities sync|add|list`. Nothing matches on a key that is not in the table. Why: the prompt forbids hardcoding; a table + seed is the smallest data-driven form; cost if wrong: a table.
- **R2 — One matching rule: dispatch still matches `runtimeRoles`; capabilities PROJECT to roles.** Every capability carries `role` (its domain's runtime role, editable). `Task.requiredCapabilities String[]` (new, default `[]`) is the planning/staffing vocabulary; `Task.requiredRole` becomes DERIVED = the role of the first required capability whose role is set (the planner may still give a bare `role` — kept for compatibility; when both exist the role wins, when only capabilities exist the role is derived; when neither, the task is unschedulable as today). A slave PROVIDES capabilities: `Slave.capabilities String[]` (new) = the normalised capabilities of its template (M46 `profileSpec.capabilities` → taxonomy keys via `normaliseCapabilities` — exact key, then label, then synonyms; unresolved strings are kept on the template as `unresolvedCapabilities` and never match) plus operator additions (`set-capabilities`); materialisation seeds `runtimeRoles` ⊇ the roles its capabilities project to (`assignCompanyTx`/`hireFromTemplate`); `set-runtime-roles` stays the override. `decide()`, review, planning and role-addressed asks are UNCHANGED. Why: the scheduler keeps its proven rule and its gates; capabilities are richer where they matter (planning, staffing, rationale); cost if wrong: a projection column.
- **R3 — Planning emits capabilities.** The plan-graph JSON (`packages/domain/src/planning/graph.ts`) gains optional `capabilities: string[]` per task (and the delta's `add` items); `PLANNING_GRAPH_INSTRUCTIONS`/`REPLAN_INSTRUCTIONS` list the taxonomy keys available in the workspace (rendered from the table, capped) and ask for them; `concludePlanning`/`concludeReplan` write `requiredCapabilities` (validated against the table; unknown keys dropped and recorded in `workspace.plan_created.payload.droppedCapabilities`) and derive `requiredRole`. The fake CLI's `plan-graph` fixtures gain capabilities in a new `m47-flow`-free way: `m41-flow`/`m8-flow` fixtures untouched; a new `plan-graph-capabilities.ndjson` used by the M47 gate.
- **R4 — Team formation is a pure domain function, staffed through the Supervisor.** `formTeam(input: { required: CapabilityKey[] (from ready/blocked tasks), roster: { slaveId, name, capabilities, runtimeRoles, busy }[], company: { companySlaveId, name, capabilities }[], catalog: { templateId, name, capabilities, division }[] }) → TeamPlan { covered: { capability, by: slaveId }[], proposals: { capability, source: 'existing_worker' | 'company_worker' | 'project_worker' | 'temporary', pick: { slaveId | companySlaveId | templateId, name }, rationale: string }[], unfillable: CapabilityKey[] }` in `packages/domain/src/capability/team.ts`, deterministic (stable ordering; the fewest new workers that cover the most missing capabilities; a template covering two missing capabilities beats two templates). The Supervisor gains a situation `capability_unstaffed` (keyed by capability; supersedes `ready_unstaffed`, which becomes its role-only fallback) and candidate actions: `assign_capability` (routine: `set_runtime_roles` on an idle existing worker whose capabilities cover it — the "existing capable worker" case), `materialise_company_worker` (proposal: one company slave → project slave, via a new single-slave `materialiseCompanySlave(workspaceId, companySlaveId)`), `hire_from_catalog` (proposal: `hireFromTemplate(workspaceId, templateId, { capability, rationale, temporary })` creating a project slave with `capabilities`, projected `runtimeRoles`, `hiredFromTemplateId`, `selectionRationale`, and — until M50 — `temporary` recorded only in the rationale/decision). `loadSupervisorWorld` gains the roster's capabilities, the company roster and the catalog's capability index. Why: pure and testable; the Supervisor's existing tiers/approval flow; cost if wrong: a function and two verbs.
- **R5 — Collaboration hints are advisory edges.** At import (M46's `importCatalog`), each `collaborationHints[]` sentence is normalised by `normaliseCollaborationHint(sentence, templates)` → `{ text, targetTemplateId | null, capability | null }` (target resolved by template name/title match, case-insensitive; capability by taxonomy match on the sentence; else unresolved) into a `CollaborationHint` table (`templateId`, `text`, `targetTemplateId?`, `capability?`, `source: 'import'`). They are shown on the profile drawer (M46) and the Organization view ("advises consulting X"), and `formTeam` uses them only as a tie-break rationale ("its profile recommends pairing with …"). They never dispatch. Why: the prompt's rule; cost if wrong: a table.
- **R6 — The Organization tab.** `/w/:id/organization` (M44's tab strip gains `Organization` between Tasks and Activity; the Graph's org mode stays under Advanced): rows = worker · kind (`company` when `companySlaveId`, `project` otherwise; `temporary` in M50) · capabilities provided (chips, taxonomy labels) · why here (`selectionRationale` | "assigned from <company>" | "seeded") · doing now (projected status + task); a "Needs" section listing `capability_unstaffed` situations with their pending proposals (approve/reject inline via M45's `ProposalRow`) and the covered/unfillable summary from `formTeam`; collaboration edges as a small list per worker. No corporate hierarchy drawing. Read model `buildOrganization(workspaceId)`.
- **R7 — Gate.** `gate:m47-team-formation` (real daemon + fake CLI + Playwright): seed the taxonomy; import the M46 fixture catalog extended with a `Security Reviewer` persona whose capabilities normalise to `security.application` and a hint "consult the Core Builder"; a workspace with Dev (`backend.api-design`) and a goal; the planning fixture emits tasks needing `backend.api-design` and `security.application`; assert `requiredCapabilities`/derived `requiredRole` on the tasks; the Supervisor raises `capability_unstaffed(security.application)` and proposes `hire_from_catalog` with the rationale sentence; approve → a project slave exists with `capabilities`, `runtimeRoles` incl. `security`, `hiredFromTemplateId`, `selectionRationale`; the task then dispatches by ROLE (a fake run starts) — proving one matching rule; the Organization tab shows the rows, the rationale, the resolved hint; `assign_capability` applies routinely for a capability an idle existing worker already provides; `droppedCapabilities` recorded for an unknown key; teardown. README `## Capabilities` + roster 21 → 22; CI.
- **Never a real model call; one vitest at a time; `web:build` last, never beside `next dev`; vocabulary `slave`; migrations additive with the Prisma 7 diff proof; existing dispatch/staffing gates (m38, m41, m10, m11) unchanged; a refusal after a write inside a transaction throws.**

## 4. Errata — where execution corrects this spec
(appended during execution)

Found while writing the plan (2026-09-11, before Task 1); each is baked into `docs/superpowers/plans/2026-09-11-m47-team-formation.md`. Reasoning with file citations is in the plan's companion notes (session scratchpad); summarised here.

- **E1 (amends R1/R2).** `Capability.role` is NOT NULL — a capability-bearing task whose derived role were null would be dropped by both world loaders.
- **E2 (amends R3).** `planTaskSchema.role` becomes optional; "role or capabilities" is checked in `validateStructure`/`validateDelta`; when both are present the role wins, when only capabilities exist the role is derived — otherwise the derivation could never be exercised.
- **E3 (amends R3).** The available-key list cannot live in `PLANNING_GRAPH_INSTRUCTIONS`/`REPLAN_INSTRUCTIONS` (pure, byte-pinned constants that carry the fake CLI's routing literals): it is a new `capabilities` run-context section rendered last in planning/re-plan runs.
- **E4.** `capability_unstaffed` is a Postgres enum member — `ALTER TYPE … ADD VALUE` in the migration (M40's `stale_task` idiom).
- **E5 (amends R7).** M47 gets its own fixture catalog `scripts/fixtures/catalog-m47/` with distinct persona names — extending `catalog-m46` would break `gate:m46`'s exact counts.
- **E6/E7 (amend R6).** The tab strip is pinned to four labels in `gate:m44` and `project-tabs.test.tsx` — both updated for `Organization`; six m14 project screenshots change and are regenerated in their own commit.
- **E8 (amends R4).** "Unstaffed" means nobody holds the projected ROLE (otherwise `assign_capability` could never fire); `capability_unstaffed` supersedes `ready_unstaffed` per task.
- **E9/E10 (amend R4).** The four existing staffing arms keep byte-identical offers (`gate:m38` answers `candidateIndex: 0`); one pass decides all situations, so `hireFromTemplate` reuses a worker hired for a sibling capability rather than duplicating.
- **E11–E14 (amend R5/R1).** Collaboration hints resolve in a second post-import pass (targets may be imported later); matching is exact-after-normalisation — real personas mostly name generic roles, so unresolved is the normal case and is shown as text; the seed's TRUNCATE list and the taxonomy write are added; `droppedCapabilities` is on both `workspace.plan_created` and `workspace.replanned`.
- **E15–E17.** Two refusal kinds in three homes; `SupervisorWorld` gains taxonomy/company/catalog with defaulted fixtures and loads them only when a task asks; `docs/ia.md` is corrected (M46 did not add the Organization tab). Minor: the seed list is 48 keys; there is no `slave.created` event (`org.changed { field: 'created' }`).
