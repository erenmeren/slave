# M50 — Ephemeral specialists

Seventh milestone of the roadmap `2026-09-10-roadmap-m44-m56.md`, on M47's team formation and M49's memory. Designed 2026-09-12 from an inventory of the worker model, the four creation sites, dispatch, resource release, the evidence a worker leaves behind, the Supervisor and the org surfaces (session scratchpad `m50-explore.md`). Every **Ruling** took the recommended option under the user's standing approval. "Slave" is this project's word for an AI worker.

**Goal.** A worker has a lifecycle: PERMANENT (it exists in the company roster), PROJECT (hired for this project), EPHEMERAL (brought in for one assignment). The Supervisor brings a specialist in for exactly one assignment when a capability gap belongs to a single task; when that assignment is over, the worker is released — its runtime roles are emptied so nothing dispatches it again, its worktrees are collected, and everything it produced (runs, contexts, events, messages, memories) stays exactly where it is. Nothing promotes a worker automatically; a person may. Every surface marks temporary workers distinctly and says when they were released.

**Facts the design stands on.** `Slave` has no lifecycle/status column and no `createdAt`; the only distinction today is `companySlaveId === null ? 'project' : 'company'`, derived in three places. `temporary` persists as one string suffix on `selectionRationale`; `TeamSource.'temporary'` exists and is never emitted; `actionOf` returns null for it. `decide()` reads only `runtimeRoles` + `busy`; `loadSlaveRows` applies no filter. Release is per task (`collectTaskWorktree`), never per worker. `deleteSlave` cascades runs, contexts, checkpoints, sent messages and worker-scoped memories. `observe` has no worker-state predicate; a hire is linked to a task only through the decision's `facts.firstTaskId`. `SupervisorSlave` carries no lifecycle.

## 1. Rulings
- **R1 — The lifecycle is a column, set at the creation site, never derived.** `enum SlaveLifecycle { permanent, project, ephemeral }`; `Slave.lifecycle SlaveLifecycle @default(project)`, `Slave.engagementTaskId String?` (the one assignment an ephemeral worker was brought in for; FK `Task`, SET NULL), `Slave.releasedAt DateTime?`, `Slave.releaseReason String?`, `Slave.createdAt DateTime @default(now())`. Creation sites: `assignCompanyTx` and `materialiseCompanySlave` write `permanent` (the worker exists in the company roster); `hireFromTemplate` writes `project`, or `ephemeral` + `engagementTaskId` when `opts.temporary` (the rationale suffix goes away — the column is the record); the seed's legacy worker is `project`. The migration (`20260912120000_m50_lifecycle`) adds the columns and ONE data statement `UPDATE "Slave" SET "lifecycle"='permanent' WHERE "companySlaveId" IS NOT NULL` (deterministic, idempotent; the default would be wrong for roster workers). Domain `packages/domain/src/lifecycle/{types,release}.ts`: `SLAVE_LIFECYCLES`, `SLAVE_LIFECYCLE_LABEL` (`Permanent` / `Project` / `Ephemeral`), `isReleasable(worker)` (pure). The three `'company' | 'project'` derivations (`capability.ts:711`, `organization.ts:25`, `brief.ts:99`) become the column.
- **R2 — One assignment: the Supervisor asks for a temporary specialist when the gap belongs to one task.** `formTeam` emits `source: 'temporary'`, `temporary: true` for a catalog pick when the capability it covers is required by exactly ONE staffable task (the "one assignment"); a gap shared by two or more tasks stays `project_worker`. `TeamInput` gains `requiredBy: ReadonlyMap<CapabilityKey, readonly string[]>` (task ids per capability; the caller derives it from the same staffable tasks). `actionOf('temporary')` → `hire_from_catalog { …, temporary: true, engagementTaskId }` (the action gains `engagementTaskId: string | null`); `carryOut` passes it to `hireFromTemplate(workspaceId, templateId, { capabilities, rationale, temporary: true, engagementTaskId })`. Reuse rule (E10) refined: an UNRELEASED ephemeral worker from the same template is reused (capabilities merged, `engagementTaskId` unchanged); a RELEASED one is never reused — a new hire gets `Name 2`. Tier stays `proposed` (a hire is money; a person approves).
- **R3 — Release is a routine Supervisor action, never a deletion.** Situation `engagement_over` (15th; subject = slave id): the worker is `ephemeral`, unreleased, its `engagementTaskId` task is terminal (done / failed / cancelled — `TERMINAL`), it has no live run and no non-terminal task assigned (`Task.assigneeId`). Offer `release_worker { slaveId, name, reason }` (15th action; tier `applied` — the routine the milestone exists for; `halted` still demotes to `proposed` like everything else) then `escalate_to_human`. Control `releaseWorker(slaveId, reason, principal?)`: `lockSlave` FOR UPDATE; refuses `slave_not_found`, `live_runs` (existing kind), `already_released` (new, 409), `not_ephemeral` (new, 409 — a person releases a project worker by deleting it, M23); writes `releasedAt = now`, `releaseReason`, `runtimeRoles = []` (`decide()` unchanged — an empty role list never matches), keeps `capabilities`, `selectionRationale`, `hiredFromTemplateId`; then collects the worker's terminal tasks' worktrees through the existing `collectTaskWorktree(taskId, 'operator')` primitive (reason `released`, a third `WorktreeCollectReason`), skipping any that refuse; appends `slave.released { slaveId, name, reason, worktreesCollected }` (53rd event; lane `work`; activity card; timeline sentence). Released workers: excluded from `formTeam`'s roster and from `staffableSlaves` (`SupervisorSlave.lifecycle` + `released: boolean`, E16-style fixture defaults), excluded from `loadSlaveRows`? — NO: `decide()`'s world loader stays untouched; the empty `runtimeRoles` is the exclusion (one rule, no second filter). `deleteSlave` is unchanged (a human's destructive act); `releaseWorker` never deletes.
- **R4 — Never auto-promoted; a person may.** No code path changes `lifecycle` after creation except `setLifecycle(slaveId, lifecycle, principal)` (control, human-only; refuses `live_runs`; `ephemeral → project` clears `engagementTaskId`, `releasedAt`, `releaseReason` and restores nothing else — the person sets roles with `set-runtime-roles`; `→ permanent` refused unless `companySlaveId !== null` (`not_in_roster`, new 409)); event `org.changed { entity:'slave', field:'lifecycle', from, to }` (the `field` union gains `lifecycle`). CLI `set-lifecycle --slave <id> --lifecycle <permanent|project|ephemeral>`; `hire … --temporary --for-task <taskId>`; `release-worker --slave <id> --reason <text>`.
- **R5 — Evidence persists.** Release touches only the four lifecycle columns, `runtimeRoles`, and worktree directories. Runs, `RunContext`, `Checkpoint`, events, sent messages, `Memory` rows (worker scope) and decisions are untouched; M49 retrieval keeps serving a released worker's LESSONs to nobody (the worker never runs again) and a released worker's memories remain on the Knowledge page under its name. The gate asserts counts before and after release.
- **R6 — Surfaces.** `OrganizationRow.kind` → `lifecycle: SlaveLifecycle` + `released: { at: string; reason: string } | null`; the row's chip prints the lifecycle LABEL (`Ephemeral` gets a distinct tone), a released worker prints `Released <date>` in the doing column, sorts last, and its Correct/Remove-style affordances are absent (there are none for workers). `ProjectBrief.team[]` gains `lifecycle` and `released` — `SlaveCard` shows the `Ephemeral` chip and greys a released card. `AllSlavesTable` gains a lifecycle column (label) and shows released ones greyed. `docs/ia.md` rule-3 compliance (raw enum in `title`/`data-lifecycle`). `gate:m44` RAW_TOKENS gains `SLAVE_LIFECYCLES` (bare words — E10-style no-op, still added). Routes: `POST /api/w/:id/workers/:slaveId/release { reason }`, `POST …/lifecycle { lifecycle }` (both gated like siblings).
- **R7 — Gate.** `gate:m50-ephemeral` (real daemon + fake CLI + Playwright): a project with one worker (`backend`) and a goal; the planning fixture emits two tasks, one needing `security.application` (nobody has it, one task) and one needing `qa.test-automation` required by TWO tasks; the Supervisor proposes `hire_from_catalog { temporary: true, engagementTaskId }` for the security gap and `hire_from_catalog { temporary: false }` for the QA gap (assert both); approve the temporary one via the real CLI → a worker with `lifecycle ephemeral`, `engagementTaskId` = the task, `createdAt` set; it is dispatched by role, finishes, the task reaches `done`; the next `supervise` raises `engagement_over` and `release_worker` is APPLIED routinely → `releasedAt`, `releaseReason`, `runtimeRoles []`, `slave.released` with `worktreesCollected 1`, the worktree directory gone; evidence unchanged (run count, RunContext count, event count for the slave, worker-scoped memory count); a later `capability_unstaffed` for the same key does NOT pick the released worker (a new hire would be `Name 2`; assert the proposal names the template, not the worker); ten more ticks → `lifecycle` still `ephemeral` (never auto-promoted); `set-lifecycle --lifecycle project` by hand → `org.changed lifecycle`; `release-worker` on a project worker → `not_ephemeral`; browser: Organization row chip `Ephemeral`, `Released <date>`, sorted last; Overview team card greyed; Workforce slaves table lifecycle column; `organization` + `overview` m14 PNGs regenerated once. README roster 24 → 25; CI step after `gate:m49-memory`.
- **Never a real model call; one vitest at a time; `web:build` last, never beside `next dev`; vocabulary `slave`; migrations additive (plus the one deterministic data statement) with the Prisma 7 diff proof; `decide()` unchanged; the M47–M49 gates unchanged; a refusal after a write inside a transaction throws; refusal kinds in three homes; labels never keys.**

## 3. Out of scope

## 4. Errata — where execution corrects this spec

Found while writing the plan (2026-09-11, before Task 1); each is baked into `docs/superpowers/plans/2026-09-12-m50-ephemeral-specialists.md`. Reasoning with file citations is in the plan's companion notes (session scratchpad `m50-plan-notes.md`); summarised here.

- **E1 (amends R2) — `actionOf` cannot see `requiredBy`, so the PROPOSAL carries the engagement.** `actionOf(proposal, capability, world)` (`packages/domain/src/supervisor/candidates.ts:128`) receives a `TeamProposal` and a world; `requiredBy` is an INPUT to `formTeam` and reachable from neither. `TeamProposal` gains `engagementTaskId: string | null`, null on all three existing arms (`packages/domain/src/capability/team.ts:126,150,171`).
- **E2 (amends R2) — "the capability it covers" is a SET.** A catalog pick covers a LIST (`TeamProposal.covers`, `team.ts:47-49`; the set-cover loop emits one proposal per pick, `:157-176`). The rule is over the UNION of task ids across `covers`: exactly one distinct id makes it temporary and is the `engagementTaskId`; zero or two-or-more keeps it `project_worker`.
- **E3 (amends R2) — `requiredBy` is computed in `teamPlanOf` and nowhere else.** That function is the only production caller of `formTeam` and already derives `required` from `world.tasks.filter(isStaffableTask)` (`candidates.ts:99`). Building the map in the same pass is what makes "the same predicate" literal. Nothing in `supervisorWorld.ts` and nothing in `apps/orchestrator` computes it.
- **E4 (amends R3) — the world cannot answer the predicate yet.** `SupervisorSlave` (`packages/domain/src/supervisor/world.ts:79-96`) has no `engagementTaskId` and `SupervisorTask` (`:17-77`) no `assigneeId`. `SupervisorSlave` gains `lifecycle`, `released` AND `engagementTaskId`; `SupervisorTask` gains `assigneeId: string | null`; the loader's two reads (`packages/control/src/supervisorWorld.ts:203-225`, `:579-594`) grow one line each; `packages/domain/test/supervisor/fixtures.ts` defaults all four.
- **E5 (amends R3) — there is no `WorktreeCollectReason` type.** The union is spelled inline in three places: `packages/control/src/collect.ts:54`, `packages/domain/src/events/schema.ts:378`, `apps/web/src/components/activity/cards.tsx:151`. `'released'` joins all three; no exported type is introduced.
- **E6 (amends R3) — the collection's actor would lie.** `collectTaskWorktree` stamps `actor: reason === 'aged' ? 'system' : 'human'` (`collect.ts:102`), and `release_worker` is `applied` — carried out by a tick with no person in it. The line becomes `reason === 'operator' ? 'human' : 'system'`.
- **E7 (amends R6) — `SlaveCard` does not read `ProjectBrief.team[]`.** It takes `SlaveCardData` from `apps/web/src/server/overview.ts:33`; `team[]` is rendered by the brief's team tile (`apps/web/src/components/project/ProjectBrief.tsx:265-311`, chip `team-company` at `:279`). Both carriers gain the fields.
- **E8 (amends R6) — the routes are `slaves/[slaveId]/…`.** The siblings are `apps/web/src/app/api/w/[workspaceId]/slaves/[slaveId]/{profile,runtime-roles}/route.ts` and their shell is `slaveControlResponse` (`apps/web/src/server/slaveControlRoute.ts:18`). A `workers/` segment would be a third spelling of one row in one URL space.
- **E9 (amends R6) — `whyHere` reads the `kind` R6 deletes** (`apps/web/src/server/organization.ts:189-197`). Its company branch keys on `companyName !== null` alone afterwards: `companySlaveId` is `SetNull` (`schema.prisma:249`), so a permanent worker can have a lifecycle and no company name.
- **E10 (amends R2) — the M47 pin is rewritten, not deleted.** `packages/domain/test/capability/team.test.ts:124-132` ("never emits the temporary source in this milestone") becomes a shared-gap case, and a new case asserts the emission. The `input()` helper (`:11-18`) gains `requiredBy: new Map()`, which keeps every other case meaning what it meant.
- **E11 (amends R4) — `org.changed.field` is spelled four times.** `packages/domain/src/events/schema.ts:399`, `apps/web/src/components/activity/cards.tsx:671` (the label map's key type), `:674-682` (the labels) and `:688` (the card's inline cast). All four move in Task 1 — `typecheck` is red without the `cards.tsx` two.
- **E12 (amends R7) — the re-raise needs a new task and an aged cooldown.** The engagement task is `done`, so `isStaffableTask` is false and the gap is gone; and `filterFresh` blocks the key for `COOLDOWN_MS` = 15 minutes (`packages/domain/src/supervisor/observe.ts:148-157`, `constants.ts:20`). The gate inserts a fresh `ready` task for the key and back-dates the earlier decision by an hour with one `updateMany`.
- **E13 (amends R2) — a reuse never rewrites a lifecycle.** The reuse branch (`packages/control/src/capability.ts:428-467`) matches on `hiredFromTemplateId` alone, so a temporary hire can land on a `project` worker — and R4 is absolute. The `findFirst` gains `releasedAt: null`; the branch writes `capabilities`/`runtimeRoles` only, leaving `lifecycle` and `engagementTaskId` as the hire that CREATED the worker set them.
- **E14 (amends R3, R4) — a release records a reason even when the caller gives none, `setLifecycle → ephemeral` writes no engagement, and only a PERSON re-arms a released worker.** `releaseWorker` normalises the sentence before the transaction and falls back to `released` for a blank one, so the column and the `z.string().min(1)` event payload can never disagree (D4 stands: no fourth refusal kind). Moving a worker INTO `ephemeral` by hand deliberately writes no `engagementTaskId`: such a worker never raises `engagement_over` — the rule needs a terminal engagement task — and the person who labelled it releases it with `release-worker`, which asks for no engagement; the same is true of the (product-unreachable) `SetNull` path. And the release is PERMANENT on every automatic path: `mergeRuntimeRoles` (`assign_capability`) refuses `already_released` under its row lock and `addRuntimeRoles` (`set_runtime_roles`) refuses it on its re-read, both before any write, because a proposal drafted before a release and approved after it would otherwise re-arm a worker `isReleasable` can never release again. `setRuntimeRoles` by a PERSON is left alone — an operator putting the roles back by hand is the deliberate exit. A released worker is also neither addressable (`rosterSection`) nor a question recipient (`questionHasRecipient`), so an asker learns in the same tick instead of waiting for `waiting_stale`.
- **E15 (amends R6) — the lifecycle chip marks everything that is not an ordinary project hire.** R6 named only `Ephemeral`; `SlaveCard` and the brief's team tile key on `lifecycle !== 'project'`, so a migrated roster worker reads `Permanent` where it used to read `company`. Kept as shipped: a person reading a project's team should see which members belong to the company roster, the label is strictly more informative than the flag it replaces, `project` — the ordinary case — still prints nothing, and only `ephemeral` takes the `waiting` tone.
