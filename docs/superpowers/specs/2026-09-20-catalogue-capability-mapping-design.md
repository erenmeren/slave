# Catalogue capability mapping — every persona reaches the taxonomy

The first of four pieces the 2026-09-20 brainstorm ordered (A: this; B: plan-first staffing with
department managers and the project mode selector; C: planning quality; D: plan-time ownership).
It is a **data milestone** with one small model-assisted pass: it grows the checked-in capability
taxonomy to cover every division the persona catalogue actually has, and adds a pass that maps a
persona's free-text capability sentences onto that taxonomy with a model, so that `formTeam`, the
Supervisor's `hire_from_catalog`, the catalogue's capability filter and the coming plan-first
staffing all see what a persona can do. Designed 2026-09-20 with the user, who took three
decisions:

1. the taxonomy grows to cover **every division of the catalogue**, written by hand into the seed
   and reviewed, not generated by a model ("a ile devam et");
2. the mapping is **model-assisted and applied directly**: it appears on the person's card marked
   as mapped, and an operator corrects a wrong key with the existing `set-capabilities` verb
   rather than approving 1,700 pairs one by one ("a ile devam et");
3. the daemon runs the same pass for personas whose mapping is missing or stale, so a catalogue
   import from the web needs no further command.

**Why now.** On the first intake-created project (2026-09-20) the planner asked for
`operations.ci-cd` and `qa.test-automation`; the Supervisor's `capability_unstaffed` situation
found nobody to propose and escalated to the human, although the catalogue holds a "DevOps
Automator" and a "Test Automation Engineer". Both templates have an empty `capabilityKeys`: the
persona says "CI/CD Excellence", the taxonomy says "CI and CD", and `normaliseCapabilities`
matches a key, a label or a reviewed synonym and nothing else (M47 R1, deliberately). Across the
live catalogue 274 of 279 templates carry no key at all, over 4,003 distinct unresolved sentences
of which eight repeat. The M47 seed's own header says why the synonym route was not taken further:
a synonym is a second correct spelling of one row, not a hint, and a broad heading like
"Performance Optimization" could sit under three rows. Semantic judgement is a model's job, and
this milestone gives it that job inside the isolation contract every other model call here already
obeys.

**Goal.** After this milestone, every active template whose `profileSpec` has capability sentences
carries a non-empty, taxonomy-valid capability set; the exact matcher stays exactly as it is; a
person opening a persona sees which keys were matched by word and which were mapped by a model;
`capabilities reconcile` and a re-import never throw a mapping away; and nothing in dispatch,
review, planning or the scheduler changes.

**Facts the design stands on** (each read out of the tree on 2026-09-20).
`packages/db/src/capabilities.ts` is the seed: 48 rows over 13 domains, key ascending, held there
by `packages/db/test/capabilities.test.ts` ("is 48 rows over 13 domains", "sorted by key
ascending", "shares no normalised spelling between two rows"). `Capability.role` is NOT NULL (M47
erratum E1) and is the string `decide()` matches after `projectRoles`. `syncCapabilityTaxonomy()`
(`packages/control/src/capability.ts`) is idempotent and runs on every import and on
`capabilities sync`; it adds what the seed has, restores a seed row, never touches a `createdBy:
'human'` row. `normaliseCapabilities` (`packages/domain/src/capability/taxonomy.ts`) is the only
matcher: exact key, exact label, exact synonym, first spelling wins. `importCatalog`
(`packages/control/src/catalog.ts`) computes `capabilityKeys`/`unresolvedCapabilities` outside the
transaction and writes them at three sites (`:521`, `:613`, `:675`); `reconcileTemplateCapabilities`
(`capability.ts:149`) re-derives both columns from `profileSpec.capabilities` and then runs
`syncPersonPool()`, which copies a template's `capabilityKeys` onto its managed people through
`effectiveCapabilities(capabilityKeys, capabilityGrants)` (`personPool.ts:145–179`). The structured
profile (`packages/domain/src/profile/spec.ts`) carries `summary`, `identity`, `capabilities[]`,
`expertise[]`, `deliverables[]`, `runtimeRole`, and a `source.mappingQuality` of
`full | partial | none`; a hand-made template has `profileSpec: null`. The daemon's global pass
(`apps/orchestrator/src/daemon.ts:504–520`) runs `tickIntakes` beside the simulations with the
process's `ModelDecider` and `supervisorModel`; a `ModelDecider` is
`({ model, prompt, maxBudgetUsd }) => Promise<ModelOutcome>` where an outcome is `answer` (text,
cost, tokens), `isolation_breach`, or a failure; `INTAKE_PER_CALL_CAP_USD` is
`SUPERVISOR_PER_CALL_CAP_USD` and `SUPERVISOR_DEFAULT_MODEL` is `claude-sonnet-5`. The CLI's
`capabilities` verbs are `sync | reconcile | add | list | backfill` (`cli.ts:424–440`). The web
renders `capabilityKeys` in `WorkforceCatalog.tsx`, `WorkforceClient.tsx` and `ProfileDrawer.tsx`.
The vocabulary gate (`scripts/gate-m26-vocabulary.mjs`) fails any tracked source or doc line
matching `(^|[^a-z])agent`, so no key, label or synonym below contains that word. The live
catalogue's divisions and counts: engineering 64, specialized 59, marketing 36, game-development
21, gis 13, security 12, design 10, sales 9, testing 9, paid-media 7, project-management 7, support
6, academic 6, spatial-computing 6, finance 5, product 5, healthcare 3, research 1. The planner's
own task roles on the first real board were `engineering`, `marketing`, `design`, `research`,
`reviewer`, `manager`, `sales`.

## 1. Rulings

**R1 — The taxonomy grows in the seed, by hand, to cover the catalogue.** `CAPABILITY_SEED` gains
the rows in §2: sixteen new domains and two additions to `security`, sixty-three rows in all, so the
seed becomes 111 rows over 29 domains. Every new row's `role` is its domain name, except
`paid-media.*`, which projects to `marketing` (a paid-media specialist is dispatched as marketing;
the planner has no reason to ask for "paid-media" as a role). The seed test's counts move to the
new numbers and its invariants (unique keys, `<domain>.<name>` shape, key ascending, domain equals
prefix, label and role present, no shared normalised spelling) stand. `syncCapabilityTaxonomy()`
carries the rows into an existing database on the next import or `capabilities sync`; no
migration is needed for them. **Why:** the user chose coverage over a minimal set; the role IS the
domain because that is the vocabulary the planner already writes. **Cost if wrong:** rows in a
table an operator can relabel, and a seed test to update.

**R2 — The exact matcher is untouched.** `normaliseCapabilities` keeps its rule (exact key, label,
synonym; no substrings, no scoring) and `unresolvedCapabilities` keeps its meaning: the sentences
the exact matcher did not resolve, verbatim. The mapping does not rewrite or empty that column,
because an operator reading it is still owed the persona's own words. **Why:** M47 R1's reasoning
holds; this milestone adds a second, clearly labelled source of keys rather than loosening the
first. **Cost if wrong:** none; the column is informational.

**R3 — A mapping is a second column with its own provenance.** `SlaveTemplate` gains three
columns (migration): `mappedCapabilityKeys String[] @default([])`, `capabilityMappingHash
String?`, `capabilityMappedAt DateTime?`. `capabilityKeys` becomes the **effective** set: the
exact matcher's keys ∪ `mappedCapabilityKeys`, deduplicated, key ascending. Every writer of
`capabilityKeys` writes that union: the three import sites, `reconcileTemplateCapabilities`, and
the mapping pass itself. A template's `Person` rows and their runtime roles follow through
`syncPersonPool()` exactly as today; `effectiveCapabilities`, `managedSlotNeedsRefresh` and
`projectRoles` are not changed. **Why:** keeping the two sources apart is what lets the drawer say
"matched" against "mapped", lets `reconcile` re-run the exact matcher without losing the model's
work, and lets a later taxonomy change invalidate only the half it affects. **Cost if wrong:**
three nullable-or-defaulted columns.

**R4 — The hash decides staleness; nothing else does.** `capabilityMappingHash` is the SHA-256
of a canonical string: the template's `profileSpec.capabilities` (trimmed, in order), `summary`,
`identity`, and the taxonomy's keys (key ascending, joined). A template is **stale** when its
`profileSpec` is non-null and parses, its `capabilities` list is non-empty after trimming, and its
stored hash differs from the computed one (a null hash is stale). A template with `profileSpec:
null`, or with no capability sentences, is never mapped: there is nothing to map from, and M47's
rule that a hand-made row is never guessed at stands. Adding a taxonomy row therefore makes every
template stale, which is the intended behaviour: the new row exists to be mapped onto. **Why:**
the hash is the one fact that answers "would the model be told anything different"; time-based or
flag-based staleness would either re-spend or go quietly wrong. **Cost if wrong:** one more model
pass over the catalogue.

**R5 — The prompt and the parse are pure domain functions.** In `packages/domain/src/capability/`:
- `buildCapabilityMappingPrompt(batch, taxonomy)` — `batch` is up to `CAPABILITY_MAP_BATCH_SIZE`
  (5) personas, each `{ id, name, runtimeRole, summary, identity, capabilities[] }`; `taxonomy` is
  the full table as `{ key, label, domain }` rows (synonyms are not sent; the model maps meaning,
  not spelling). The prompt says what a capability key means here (a thing a worker can be asked
  to do, matched against tasks), asks for **at most `CAPABILITY_MAP_MAX_KEYS` (8) keys per
  persona, chosen from the list and only the list, most central first**, allows an empty list,
  forbids inventing keys, and asks for one JSON object and nothing else:
  `{"personas":[{"id":"<id>","keys":["<key>", …]}, …]}`. The prompt names the catalogue by its
  own word for it, "persona", and never by a source repository's name.
- `parseCapabilityMappingAnswer(text, batch, taxonomy)` — takes the first JSON object in the text
  (the intake's `firstJsonObject` discipline), validates the envelope with zod, and returns per
  persona `{ id, keys, dropped }`: `keys` are the answer's keys that exist in the taxonomy,
  deduplicated, truncated to `CAPABILITY_MAP_MAX_KEYS`; `dropped` are the strings that were not
  keys, kept for the report. A persona the answer does not mention, or mentions with a malformed
  entry, is **absent** from the result (not empty): absent means "no answer, try again", empty
  means "the model said nothing applies", and R6 treats the two differently. An answer with no
  JSON object, or whose envelope fails, returns `null`.
**Why:** the same shape as the intake's `buildIntakePrompt`/`parseIntakeAnswer`, testable with
fixture strings and no database. **Cost if wrong:** two functions.

**R6 — One control verb does the pass, and it never spends twice for the same fact.**
`mapTemplateCapabilities(input)` in `packages/control/src/capabilityMapping.ts`:
- input: `{ decider: ModelDecider, model: string, only: 'stale' | 'all', dryRun: boolean,
  batchSize?: number, maxBatches?: number, maxBudgetUsdPerCall?: number }`;
- selects templates (`only: 'all'` ignores the stored hash but still skips the never-mapped
  cases of R4), id ascending, in batches of `batchSize` (default `CAPABILITY_MAP_BATCH_SIZE`),
  up to `maxBatches` batches when given;
- per batch: builds the prompt, calls the decider with `maxBudgetUsd` =
  `CAPABILITY_MAP_PER_CALL_CAP_USD` (= `SUPERVISOR_PER_CALL_CAP_USD`, the same constant the intake
  uses) unless overridden, parses the answer; for every persona **present** in the parse it writes
  `mappedCapabilityKeys`, `capabilityMappingHash` (the hash computed before the call),
  `capabilityMappedAt`, and the effective `capabilityKeys` union (R3), in one transaction per
  batch; a persona absent from the parse, or a whole batch whose answer is `null`, an
  `isolation_breach` or a failure, is left exactly as it was and is counted, so the next run
  retries it; a batch's failure never stops the following batches;
- `dryRun: true` builds prompts, calls the model, parses, and writes nothing — it returns what it
  would have written, per persona, for the CLI to print;
- after the last batch, unless `dryRun`, runs `syncPersonPool()` so managed people pick up their
  keys on the same call (the `reconcile` precedent, M55 final review Important 4);
- returns `CapabilityMappingReport { considered, stale, calls, mapped, unchanged, absent,
  failedBatches, droppedKeys, costUsd, unmeasuredCalls, pool }` where `unchanged` counts personas
  whose written set equals what was stored, `absent` the R5 absences, `droppedKeys` the total of
  invented keys, `costUsd` the sum of measured call costs and `unmeasuredCalls` the calls whose
  outcome carried no cost (the intake's own honesty rule).
`reconcileTemplateCapabilities` changes in one place: the written `capabilityKeys` is the R3 union
with the row's stored `mappedCapabilityKeys`, so a reconcile after a mapping loses nothing. The
three import sites write the union with the existing row's `mappedCapabilityKeys` when the row
already exists (cases (b)/(c) in `importCatalog`) and with `[]` for a new row (case (a)), and a
changed file in case (c) leaves the hash as it is — R4's next comparison decides whether the
change was one the model would care about. **Why:** batches bound the prompt; the hash bounds the
spend; per-batch transactions bound the blast radius of a bad answer. **Cost if wrong:** a verb
with a report.

**R7 — The CLI verb and the daemon pass are two callers of R6, nothing more.**
- `capabilities map [--all] [--dry-run] [--batch <n>] [--max-batches <n>]` in
  `apps/orchestrator/src/cli.ts`, listed in the help block beside `reconcile`. It builds the
  decider exactly as `daemon` does (`buildModelDecider()`, the deny-all hook), reads the model
  from `SLAVEOFAI_SUPERVISOR_MODEL` with `SUPERVISOR_DEFAULT_MODEL` as the fallback, prints the
  report as JSON, and in `--dry-run` prints one line per persona: name, then the keys, then the
  dropped strings if any. Exit 0 whether or not anything was stale; exit 1 only when the verb
  itself throws.
- The daemon's global pass gains, after `tickIntakes`, `tickCapabilityMapping({ decider, model })`
  in `packages/control/src/capabilityMappingTick.ts`: when a decider exists it runs
  `mapTemplateCapabilities({ only: 'stale', dryRun: false, maxBatches: 1 })` — **one batch per
  pass**, so a freshly imported catalogue of 279 personas is mapped over about 56 passes at the
  daemon's own pace rather than in one burst, and a taxonomy change re-maps at the same pace; when
  no decider exists it returns `{ skippedNoDecider: true }`. The daemon prints the report line
  when a call was made or the decider was missing, exactly as it does for `intakes`. The pass is
  wrapped by the same `try` as the intake pass: a failure is logged and the next pass starts
  clean. Two daemons running the pass at once can map the same batch twice; the second write is
  the same content, and the hash makes the third pass skip it. That is the intake's own
  "at-most-twice" tolerance and is accepted here for the same reason.
**Why:** the user wants an import from the web to need no further command, and one batch per
pass is the daemon's existing rhythm for model spend. **Cost if wrong:** a CLI verb and a tick
function of thirty lines.

**R8 — The surfaces say which keys were matched and which were mapped.** The three web renderers
of `capabilityKeys` receive both sets: the catalogue card and the workforce person card keep
showing the effective set; the persona drawer (`ProfileDrawer.tsx`) shows the effective set with a
`data-provenance="matched" | "mapped"` on each chip and a one-line note when the mapping is
missing or stale ("capabilities not yet mapped" / "mapping is stale"), so a person reading a
persona knows what a filter will find. The read models that feed those components
(`packages/control/src/catalog.ts` `catalogTemplate*` selects, `:1111` and neighbours) add
`mappedCapabilityKeys` and `capabilityMappedAt`; `capabilities list` is unchanged; a new
`capabilities map-status` is NOT added — the `map --dry-run` report and the drawer are the two
places to look. **Why:** the user asked for the mark on the card; a second listing verb would
duplicate the report. **Cost if wrong:** attributes on chips.

**R9 — Nothing downstream changes.** `decide()`, `loadWorld`, `formTeam`, `teamPlanOf`,
`hire_from_catalog`, the planner prompt, the catalogue search filter (`capabilityKeys: { has }`)
and `syncPersonPool` read `capabilityKeys` as they do today and therefore see the effective set
without a line of change. No new `EventType`, no event written by the pass (the report is printed
and returned; the daemon's stdout is the record, as for `intakes`). No gate is added; the m46 and
m55 gates are not touched.

## 3. The prompt's contract, spelled out

The prompt is built from constants in `packages/domain/src/capability/mapping.ts` and says, in
this order: what the system is (a company of specialists whose work is matched to tasks by
capability keys); what a key is (one thing a specialist can be asked to do; the list is closed);
the taxonomy as `key — label (domain)` lines; then each persona as a block: `id`, `name`, the
runtime role the catalogue gave it, `summary`, `identity`, and its capability sentences as
bullets; then the instructions: choose at most eight keys per persona, from the list only, the
most central first, an empty list when nothing fits, never a key that is not in the list, no
prose; and the answer shape. The block for one persona is bounded by `CAPABILITY_MAP_SENTENCE_CAP`
(40 sentences, the catalogue's own maximum) and the whole prompt by five personas, which keeps a
call well under the intake's per-call cap on the default model.

## 5. Out of scope

The taxonomy's role vocabulary beyond the domain names (which roles a department manager holds,
how `manager` is assigned) is B's. Re-mapping on a schedule, a web button to trigger the pass, and
a per-key confidence score are not built: the hash and the daemon pass cover the first, the
daemon covers the second, and the third has no reader yet. `unresolvedCapabilities` is not
pruned by the mapping (R2).

## 6. Errata

E1 (T1): `capability.test.ts`'s "operator adds a brand-new key" fixture used `legal.contracts`,
which is now a seed key; the fixture was renamed to `legal.playbook`, and the README's example was
changed for the same reason.

E2 (T5): the exact half is recomputed in `loadCandidates` with `normaliseCapabilities` rather than
derived by subtracting `mappedCapabilityKeys` from `capabilityKeys` — subtracting would have lost a
key that belongs in both halves on a re-map that dropped it.

E3 (T5): `rows` and `droppedKeys` are batch-local counters folded into the running totals only after
each batch's transaction commits; a thrown transaction counts that batch as failed and does not stop
later batches from running.

E4 (T5): only ACTIVE structured templates are mapped (an inactive persona cannot be hired, so
mapping it spends for nothing; once activated it is stale and the daemon maps it); `dryRun`
classifies before deciding, so `rows`/`mapped`/`unchanged` mean what a real run would do; a
non-integer `batchSize` or `maxBatches` falls back to its default.

E5 (T6): `all` joined the CLI's valueless flag set so `--all --dry-run` parses, and the fake CLI's
mapping arm is wired in the `complete` mode only.

E6 (T7): the daemon's mapping call is detached, like the intake's (a module-level in-flight promise,
drained by `drainCapabilityMappingCalls()` at shutdown); `tickCapabilityMapping` returns
`{ skippedNoDecider, skippedInFlight, started, stale }`, and the detached call logs its own
`{ capabilityMappingPass }` line when it settles — R7's "one batch per pass" still holds, but the
pass itself never waits on the call.

E7 (T8): the drawer has four states with precedence inactive (never mapped) → none (never mapped) →
stale → mapped; `capabilityMappingStale` includes `active`; `capabilityMappedAt` crosses to the
client as an ISO string like the other two dates; chips render only when there is at least one key,
so "no capabilities recorded" never prints above the persona's bullets.

E8 (T1, surfaced by T9's ladder): R1 grows the seed to 111 rows, past `runContext.ts`'s
`CAPABILITY_KEYS_IN_PROMPT` (80) — a constant no task touches. A planning prompt built off the real
taxonomy is now genuinely capped, so `runContext.test.ts`'s "shows a planning run the taxonomy
keys" test (pre-existing, not part of this plan) asserted a key and a `capped: false` that no
longer held; it was updated to a key that still sorts inside the first 80 and to `capped: true`.
