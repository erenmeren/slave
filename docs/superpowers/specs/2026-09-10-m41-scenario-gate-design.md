# M41 — The end-to-end scenario gate: one story through the whole system

Seventh milestone of the Supervisor sequence (M35 pipeline honesty, M36 messaging, M37 run context, M38 Supervisor, M39 mailbox, M40 requirement versioning). Designed 2026-09-10 (overnight) under the user's standing authorisation of 2026-09-09; every **Ruling** below was taken with the recommended option and can be reworked in the morning. "Slave" is this project's word for an AI worker.

**Goal.** One gate, `gate:m41-scenario`, drives one realistic software-team story through the WHOLE system with a real daemon lineage and the fake `claude` CLI, and at the end asserts the truth of every operator surface at once. Nothing new in the product unless the story exposes a gap; a gap is a defect fixed in this milestone (§7), never a workaround in the gate.

**Why now.** Each earlier gate proves one seam under a real daemon: m35 integration truth, m36 ask/answer across a restart, m37 the recorded prompt, m38 staffing/budget, m39 the mailbox, m40 re-planning. None runs the seams in SEQUENCE. The sequence's claim — a team that coordinates itself and tells the truth about its state — is only proven when one run crosses all of them. M42 (external catalog import) reuses this story as its regression net.

## 1. Rules that bind every part

- **One story, one script, one daemon lineage.** The gate runs a real `daemon` subprocess with the fake CLI throughout. It restarts the daemon only where a fixture switch demands it (the M40 `--replan-cancel` argv idiom) and proves each restart the way `gate-m36-messaging.mjs` does (pid gone, `findRealDaemonPids()` empty, new pid ≠ old). No one-shot `tick` for anything the daemon can drive.
- **The fake CLI serves every arm in one mode — Ruling R1.** New mode `m41-flow` in `packages/providers/test/fake-claude.mjs`, prompt-sniffing precedence `supervisorArm` (`"candidateIndex"`) → `answerArm` (`"sources"`) → `replanArm` (`"replan"`) → planning (`"task graph"`, replays the NEW fixture `plan-graph-scenario`, R4) → review (`"verdict"` → `review-approve`) → work. A work run is the ASKING leg (the m36 body: `complete` with the `<slave-ask>` envelope from `FAKE_CLAUDE_ASK_JSON` appended to the last assistant text block) only when ALL of: argv carries `--ask-on-task <taskId>`, the prompt contains that task id, and argv has no `--resume`. Every other work run — and every `--resume` leg — writes `m41-work.txt`, commits it as `Fake Claude`, and replays `complete`. Argv is the channel because a run's spawn args are the gate's only deterministic per-daemon knob (M39 E6); the task id is the discriminator because two workers share the `backend` role and only one of them may ask.
- **Ruling R2 — act 3 uses the Supervisor's sourced path with NO new threshold seam.** The question is addressed to the `qa` ROLE, which no slave in the scenario holds, so `unanswerable_question` fires on the Supervisor's next pass without any staleness wait (`observe.ts`: "however fresh it is, nobody can answer it"). The daemon carries the default `supervisor-answer` fixture; `verifySources` finds the cited sentence in the asking task's own description (R4). The `SLAVEOFAI_WAITING_STALE_MS` knob considered in the draft is NOT built — a peer answer (`<slave-answer>`) would prove M36 only, and a threshold seam would add a product surface for a test.
- **Ruling R3 — the M40 residuals ride along**, as a first task, each with its own test or a doc-only commit: (a) `apps/orchestrator/src/cli.ts` `replan-status` help text says "unfinished task" — E8 made `boardVersion` the max over EVERY task; (b) `scripts/gate-m40-requirement-versioning.mjs` stage-3 comment claims E8 regression-guard power it lacks (the RED proof is `planning.test.ts`'s "finished board stays current" case) — reword; (c) `apps/orchestrator/src/replan.ts` `concludeReplan` docblock "Nothing here may throw past this function" is untrue of `failRun` during a database outage — one honest sentence on both docblocks; (d) the goal-history route's body validator gets its non-numeric-version test if it has none (check first; skip with a ledger note if covered).
- **Ruling R4 — the story owns its plan fixture.** `packages/providers/test/fixtures/plan-graph-scenario.ndjson`: a copy of `plan-graph.ndjson` whose three tasks are `core` (backend, no deps), `api` (backend, depends on core), `polish` (backend, depends on api) and whose `core` description contains, verbatim, the sentence `supervisor-answer.ndjson` cites (`PostgreSQL on port 5433`, see `gate-m39-supervisor-mailbox.mjs` `SOURCED_QUOTE`). The stock `plan-graph` descriptions carry no such sentence, so a sourced answer over them is impossible; changing the stock fixture would silently change m8/m40's measurements. Same `total_cost_usd` as `plan-graph` so the spend table stays one lookup.
- **Ruling R5 — a dedicated reviewer.** Slaves: `Atlas` (`['manager']`), `Dev` (`['backend']`), `Ops` (`['backend']`), `Rae` (`['reviewer']`). Nobody holds `qa`. A reviewer that also codes could be refused as the author of the work it reviews or be dispatched a `backend` task mid-review; a fourth slave removes both ambiguities at zero product cost. `dispatchReview` must be able to pick Rae — if the reviewer selection excludes nothing, still keep Rae (the story reads better).
- **The gate asserts, it never fixes.** Every stage prints every measured value before asserting it; a failed assertion dumps rows (`dumpGateRows`, m39/m40 style) and exits 1; teardown in FK order runs on every exit path; daemons are stopped on every exit path.
- **The truth table is asserted through the surfaces an operator sees**, not only through Prisma: `buildTasksSnapshot` and `buildOverviewSnapshot` (`apps/web/src/server/{tasks,overview}.ts`), `buildSupervisorView` (`apps/web/src/server/supervisor.ts`), `listGoalVersions`, `workspaceSpend`, `workspaceStats` (`packages/control`), and the CLI verbs `status`, `supervisor-decisions`, `goal-history`, `replan-status`, `show-context`, `messages`. The gate imports web builders from `apps/web` the way an existing gate imports control's `dist` — if no existing gate imports `apps/web/src/server/*`, Task 2 decides between `tsx`-free import of a built output and a thin control-level helper; **Ruling R6:** prefer a control-level read helper only if `apps/web` cannot be imported from a `node` script without a bundler; then the helper lives in `packages/control` with a unit test and the web builder is left as is.
- **No real model call** (`SLAVEOFAI_CLAUDE_BIN=node`, `SLAVEOFAI_CLAUDE_ARGS="<fake-claude.mjs> --fixture m41-flow …"`, `SLAVEOFAI_REQUIRE_FAKE_CLI=1`); one vitest process at a time; no migration unless a gap needs one; vocabulary `slave`; `web:build` last and never while `next dev` runs.

## 2. The story — acts and what each proves

Workspace `Scenario Co` on a temp git repo (`makeRepo()` as m40), `autoMerge: true`, `verifyCommands: ['true']`, a `providerConfiguration` row (`claude_code`), budget `$20`, Supervisor enabled (the default). Costs come from the fixtures' terminal `result` lines READ AT RUNTIME, never hard-coded (m39 hard-codes $0.01/$0.02 for the two decision fixtures; this gate reads all six).

1. **Plan.** Daemon-1 (`--fixture m41-flow --ask-on-task` is NOT yet known, so daemon-1 carries no ask flag) — `set-goal` v1 through the CLI prints `{version:1, sha256}`; the manager's planning run lands core → api → polish, all `ready`, all `goalVersion 1`; `workspace.plan_created { goalVersion 1 }`; the planning run's `RunContext` manifest has `planning_goal.version 1` and no `replan` section; `replan-status` prints `willReplan false, blockedBy null`. **Then daemon-1 is stopped BEFORE any work run starts** — the gate must stop it the instant the three tasks exist (poll at 50 ms; if a work run has already started, the gate fails loudly rather than tolerating it, so the timing claim is measured). Alternative considered and rejected: seeding the plan by hand (the story must start with the manager).
2. **Work + ask.** Daemon-2 carries `--ask-on-task <coreId>` and `FAKE_CLAUDE_ASK_JSON` addressed to `recipientRole: 'qa'` asking what database the service talks to. Core dispatches (Dev or Ops — the gate records which); the run pauses `waiting_for_answer`, the task is `waiting`, one `question` message exists, `attempt` 0, no `run_failed`. The run's `RunContext` manifest `task.sha256` equals the hash of the task text the renderer hashed (compute through the same exported helper the product uses — the gate must not re-implement the hash). `api` and `polish` are still `ready`/blocked: nothing else may move (api depends on core).
3. **Answer.** Without restarting, the Supervisor's next pass observes `unanswerable_question` (no `qa` holder), chooses `answer_question` (`supervisor-decision` fixture), drafts (`supervisor-answer` fixture), verifies the quote against core's description, and the decision row is `applied` with `draft.confidence 'sourced'`, `modelCalled true`, cost = choice + answer; one `answer` message with `answeredBy: 'supervisor'`; a later tick's `deliverAnswers` resumes the run (`run_resumed`, same `sessionId`); the resumed leg commits `m41-work.txt`. Assert exactly one `SlaveRun` for core, one `answer`, and — through `buildSupervisorView` — `mailbox.answeredBySupervisor24h 1` (use the field the view actually exposes; the plan names it after reading `supervisor.ts`).
4. **Verify → review → merge → integrate.** Core's run succeeds, verify passes (`true`), the task goes `reviewing`; Rae's review run replays `review-approve`; core is `done`; `runMergePass` merges (`autoMerge`), `integratedAt` set, `task.integrated`; `api` now has `dependenciesDone true` through the orchestrator's own `loadWorld`; `api` dispatches and completes the same way (ask flag names core only, so api's work run commits without asking) — the gate waits until `api` is `done` and integrated too; `polish` remains `ready` (its dependency `api` done → it may dispatch — **the gate stops daemon-2 as soon as `api` is integrated and BEFORE `polish` has a run**, measured the same way as act 1; if polish already started, fail loudly). Spend so far = Σ fixture costs for every run + the two decision calls (a printed table: kind, count, unit cost, subtotal).
5. **Goal change → re-plan.** `set-goal` v2 (the goal now asks for an endpoint doc); `goal-history` prints v2 before v1 with a diff; `replan-status` prints `willReplan true, blockedBy null`. Daemon-3 carries `--replan-cancel <polishId>` and no ask flag. The re-plan run's manifest has a `replan` section (v1 → v2), its prompt carries `THE GOAL CHANGED`; `workspace.replan_started`; on conclusion ONE new task `docs` (`ready`, `goalVersion 2`), ONE pending `stale_task` proposal naming polish, `workspace.replanned { added:[docs], proposedCancellations:[polish], droppedCancellations:[], failedProposals:[] }`; core and api untouched at `goalVersion 1`. **Daemon-3 is stopped right after `workspace.replanned`** so that `docs` (backend, ready) does not dispatch — it is the last act's "what comes next", not work done. (`polish` cannot dispatch while its proposal is pending? — it CAN: a proposal does not block scheduling (R1 of M40). So the gate must stop daemon-3 before polish or docs dispatch: measure, fail loudly if either has a run.)
6. **Approve.** `approve-decision --id <proposal>` through the CLI → polish `cancelled`, `task.cancelled { goalVersion 1 }`, the decision `applied`.
7. **Truth table.** With no daemon running, assert from the read models and CLI, printing each first:
   - tasks: core `done`, integrated, v1; api `done`, integrated, v1; polish `cancelled`, v1; docs `ready`, v2, stale badge data = tasks with `goalVersion < 2` that are non-terminal → 0 (core/api are done, polish cancelled) — and the tasks snapshot's stale marker agrees;
   - goal history: `[v2, v1]`, each with sha256, v2's diff non-empty;
   - Supervisor: `supervisor-decisions` lists exactly two rows (answer applied, stale_task applied), `pending 0`; the view's report `applied` count ≥ 2 and no `escalated`;
   - messages: `messages --workspace` shows the question and its answer; the thread is 2 long;
   - spend: `workspaceSpend.spentUsd` equals the printed table's total to 1e-9 (runs: planning 1, work 2 legs ×2 tasks? — the asking leg and the resumed leg are ONE run with ONE terminal result each? The plan must read `collect.ts`: a paused run's first leg has no `result` cost recorded if the stream ends in `<slave-ask>`… the fake replays `complete` including its `result` line, so the cost is recorded for BOTH legs — confirm in Task 2 and put the truth in the table), review runs 2, re-plan 1, decisions 2 (answer: choice+answer; stale_task: 0 — rules, no model);
   - events: a printed count per type with an expectation for the load-bearing ones (`task.created` 4, `task.cancelled` 1, `task.integrated` 2, `workspace.plan_created` 1, `workspace.replan_started` 1, `workspace.replanned` 1, `slave_message_sent` 2, `run_paused` 1, `run_resumed` 1, `supervisor.decision_*` per M38 names) and `guardrail.tripped` 0;
   - `status --workspace` prints no halt; `workspaceStats` agrees on task counts; `show-context` on the re-plan run renders the replan section.
8. **Teardown** in FK order; every daemon stopped on every exit path (`finally`).
